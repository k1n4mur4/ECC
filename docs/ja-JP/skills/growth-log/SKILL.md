# Growth Log スキル

> **問題:** 多くの人は学習ログとして「Xのバグを修正した」と書きます。それは日記であって、学習の成果物ではありません。本物の成長ログは*パターン*を抽出し、次回それを認識できるようにします。
>
> **このスキルが教えること:** セッションをまたいで積み上がる学習エントリの書き方です。Markdownファイル、Notion、Obsidian、プレーンテキストなど、どのノートシステムでも使えます。テンプレートは汎用的なので、自分の環境に合わせて調整してください。

## 有効化するタイミング

- 複雑なタスク（複数ファイル、新機能、アーキテクチャ変更）を完了した後
- 失敗、ミス、または「思ったより大変だった」と感じた後
- ある期間に学んだことを振り返りたいとき

**有効化しない場合:** 些細な変更（タイポ修正、1行の微調整、デバッグを伴わない設定値の変更）。判断基準は、*このタスクにデバッグ、やり直し、ロールバック、または自明でない意思決定が含まれていたか*です。含まれていればエントリを書きます。含まれていなければスキップします。

## 3つのルール

### ルール1: 失敗 > 成果

失敗は成功よりも学びの密度が高いものです。見つけるのに2時間かかったバグ1つは、一度でうまくいった機能3つよりも多くを教えてくれます。

**悪い例:** 「ログインフローを正常に実装した。」
**良い例（Web開発）:** 「ログインフロー: Chrome 128以降でCookieの`SameSite`のデフォルトが`Lax`になったため、セッショントークンが保持されなかった。パターン: クロスオリジンでは常に`SameSite=None; Secure`を明示的に設定する。認識するシグナル: ブラウザのアップグレード後、またはオリジン境界をまたぐときに認証が壊れる。」
**良い例（データパイプライン）:** 「`pandas.read_csv(dropna=False)`は`len()`が有効行として数える幅ゼロの行を保持するため、CSVインポートが空行のせいでエラーも出さずに失敗した。パターン: 行数の検証の前に必ず`df.dropna(how='all', inplace=True)`を実行する。」

### ルール2: 伯楽の原則（伯乐原则）

新しいエントリを書く前に問いかけます。*「これは、すでに記録したものと本質的に同じではないか？」*

根本原因が同じで症状が異なる場合は**統合**し、重複させません。根本原因が新しい場合は新しいエントリにします。

**確認方法:** 書く前に、根本原因のキーワードで既存のエントリを検索します。一致するものがあれば、重複を作らず、既存のエントリの下に新しい症状を追加の例として加えます。

**例:** 「ファイル作成後に出力インデックスの更新を忘れた」と「タスク後にスキル評価の更新を忘れた」は、根本原因（自動的なキャプチャのトリガーがない）が同じです。「タスク後のキャプチャ漏れ」についての1つのエントリに統合します。

### ルール3: 転用可能であること

すべてのエントリは次の問いに答えなければなりません。*「次に似た状況に直面したとき、自分は何を違うやり方でするか？」*

その1文が書けないなら、まだパターンを抽出できていません。

**具体的な出来事からパターンを抽出する方法:**
1. 何が起きたかを1文で述べる
2. 根本原因に到達するまで「なぜ？」を繰り返す（通常は3〜5回のなぜ）
3. 一般化する: 「これはどのクラスの問題か？」（「Chrome 128のバグ」ではなく「ブラウザのデフォルト変更が既存の動作を壊す」）
4. 「次に[シグナル]を見たら、[アクション]する」という形に整える
5. シグナルに名前を付ける: このパターンが働いていることを示す、具体的に観察可能なものは何か？

## エントリテンプレート

**スコープ:** 1つの明確な根本原因につき1エントリ。標準的な長さは4〜8文です。書くのに2分以上かかるなら、出来事を語っています。30秒未満なら、掘り下げが足りません。

```markdown
## [タイトル: 出来事ではなくパターン]

### Context
- 何をしようとしていたか？
- 何がうまくいかなかったか / 何が意外にうまくいったか？

### Root Cause / Core Insight
- 症状だけでなく、根底にあるメカニズム

### The Pattern (transferable)
- 次に[似た状況]になったら、[具体的なアクション]する。
- Signal to recognize: [このパターンが働いていることを示す観察可能なものは何か？]

### Related
- [entry-name](../path/to/related-entry.md)
```

## エントリタイプ

4つのタイプはすべて上記のテンプレートを使用します。タイプによって、どのセクションに最も重みを置くかが決まります。

| タイプ | 使用するタイミング | 重点 | タイトル例 |
|------|------------|----------|---------------|
| **Failure** | 何かが壊れた、デバッグが必要だった、またはやり直しが必要だった | Root Cause | 「Config inheritance ≠ behavior inheritance across sessions」 |
| **Methodology** | 作業から再現可能なプロセスが生まれた | Context / Pattern | 「PPT → open-book exam study guide: three-layer structure」 |
| **Pattern Discovery** | ツール、システム、思考についての再利用可能な洞察 | Pattern セクション | 「PR description template: describe the gap, not the feature」 |
| **Capability Change** | 測定可能なスキルの向上 | Context（前と後の比較） | 「Git: from clone/push to independent PR with 12 commits」 |

## 品質チェックリスト

成長ログのエントリを確定する前に確認します。

- [ ] タイトルは出来事ではなく*パターン*を名指ししているか？
- [ ] 「次回は…する」という文があるか？
- [ ] 「認識するシグナル」は、次回そのパターンに気づけるほど具体的か？
- [ ] 書く前に既存のエントリで重複を検索したか？（伯楽の原則）
- [ ] 根本原因が症状と区別されているか？
- [ ] 関連するメモリ同士がクロスリンクされているか？
- [ ] エントリは4〜8文か？ 短すぎれば浅すぎ、長すぎれば出来事を語っています。

## アンチパターン

- 避ける: 「決済モジュールのバグを修正した」（パターンではなく出来事）
- 避ける: gitのコミットメッセージをそのままコピーする（コミットは何が変わったかを記述し、ログはなぜそれが重要かを抽出します）
- 避ける: コミットごとにエントリを書く（パターンが現れたときだけ書く）
- 避ける: 転用可能な文を省略する（それがなければただの日記です。これは必須です）
- 避ける: 同じパターンを異なるタイトルで重複させる（伯楽の原則に違反します。書く前に検索してください）

## 保存先

ノートを保管している場所に保存します。一般的なパターン:
- `growth-log/` ディレクトリ内のMarkdownファイル（1日1ファイル: `YYYY-MM-DD.md`）
- Notion、Obsidian、またはお使いのノートアプリの専用セクション
- 一貫した命名規則を持つプレーンテキストファイル

1つの規則を選び、それを守り通してください。形式よりも検索しやすさのほうが重要です。

## Delivery Gate を使用する場合

`delivery-gate` Stopフックは、ファイルシステムのタイムスタンプを使って、学習ファイルが今日変更されたかどうかを確認します。このスキルは*何を書くか*を教えるので、delivery-gateが確認するファイルには、空のタイムスタンプではなく有用なパターンが実際に含まれます。

```
Task completes → delivery-gate checks: was the learning file touched today?
  → Stale (no file modified): block — "what did you learn?"
  → Fresh (file touched): pass — this skill ensures the content is useful
```

方法論のない強制は、空のエントリを生みます。強制のない方法論は、記録し忘れを生みます。それぞれ単独でも有用ですが、組み合わせることでループが閉じます。
