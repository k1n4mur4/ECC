# ドキュメントガバナンスルーター

このオプションのルーターは、ドキュメントガバナンスの依頼に対して、最小限で済む既存の ECC 機能を選択するために使用します。このルーターは並列のプロジェクト管理システムを作らず、ドキュメントをコード、テスト、Issue、メンテナーの決定よりも優先される権威として扱うこともありません。

## 発動するタイミング

- ユーザーがドキュメントガバナンスまたはプロジェクト知識の整理を広く求めたとき。
- 依頼が複数のドキュメントの役割にまたがり、適切な担当が不明確なとき。
- ユーザーが決定論的で読み取り専用のドキュメント整合性監査を求めたとき。
- ファイルを追加する前に、プロジェクトが既存のドキュメントソースを把握する必要があるとき。

具体的なスキル名が指定されている場合や、宛先がすでに明確な通常のドキュメント編集では発動しないでください。

## ロール契約

`.governance/docs-map.json` やデフォルトのファイル名を解釈する前に、[成果物ロール契約](../../../../skills/docs-governance/references/artifact-role-contract.md)を読んでください。事実を所有するのは論理的なロールであり、ファイル名はフォールバックです。リポジトリで確立済みの信頼できる情報源を再利用し、デフォルトのロールを満たすためだけに 2 つ目のドキュメントを作成してはいけません。

## 意図のルーティング

| ユーザーの意図 | ルーティング先 |
|---|---|
| 憲章、マップ、ステータス、履歴の骨格を導入または維持する | `living-docs-governance` |
| 元に戻すことが難しいアーキテクチャ上の意思決定を記録する | `architecture-decision-records` |
| 重要な欠陥に対する実行可能なリグレッションを残す | `ai-regression-testing` (スタンドアロンの Pi コアでは別途インストール) |
| 検証可能なゴールとフィードバックループを定義する | `loop-design-check` (スタンドアロンの Pi コアでは別途インストール) |
| マッピングされたロール、ローカルリンク、ADR インデックス、TEST-ID、孤立している可能性のあるドキュメントを確認する | 同梱の読み取り専用監査を実行する |

どの行にも当てはまらない場合は、複数のワークフローを推測で組み合わせるのではなく、担当の曖昧さを説明してください。

## 読み取り専用監査

監査は、ユーザーが監査を求めた場合、または合意済みの検証ステップである場合にのみ実行します。まず対象のスキルディレクトリを解決し、その後で次を実行します。

```bash
python3 <docs-governance-skill>/scripts/audit-docs.py --root <repository> --scope full
```

利用可能なスコープは `spine`、`context`、`adr`、`artifacts`、`modules`、`full` です。モジュールの証跡については、実際のビジネス境界を明示的に選択してください。ディレクトリだけでは境界づけられたコンテキストの証明にはなりません。複数の境界を指定する場合は `--module` を繰り返します。

```bash
python3 <docs-governance-skill>/scripts/audit-docs.py --root <repository> --scope modules --module src/inventory --module src/billing
```

`modules` には選択されたディレクトリが必要です。`full` も `--module` を受け付けます。それ以外のスコープは、要求されたチェックを黙ってスキップするのではなく、`--module` を拒否します。モジュールチェックは、ローカルの `AGENTS.md` と `CONTEXT.md` を探し、見つからない場合は最も近い祖先ディレクトリと、マッピングされたプロジェクトソースを共有候補として報告します。ローカルファイルが欠けていることはレビューを促すものであり、ディレクトリごとに 2 つのファイルを作成せよという要求ではありません。このチェックは、選択されたファイルのローカルリンクを検査します。検査には成果物監査と同じ、リポジトリ内に閉じたパスの検査と Markdown のチェックを使い、各ソースからの相対パスで行います。ファイルが存在することだけからハーネスによる読み込みを推測することはありません。

機械的なチェックの後、実際のモジュールコード、呼び出し元、契約、テストを確認してください。責務と import/呼び出しの境界を文書化されたルールと、用語を正規のコンテキストソースと、それぞれ比較します。具体的な矛盾はソースのパスとともに報告し、ビジネス上の意図が不明な点は未検証のままにします。共有候補が実際にそのモジュールをカバーしていること、およびホストが該当する指示を読み込むことを確認してください。契約と ADR の既存の担当を再利用し、それらを `AGENTS.md` にコピーしないでください。リンクのチェックを通過しても、この意味的なレビューを通過したことにはなりません。

監査はリポジトリのファイルと Git 履歴を読み取りますが、何かを作成、書き換え、アーカイブ、ステージ、コミットすることはありません。報告内容は次のとおりです。

- 決定論的なチェックが通過した場合は終了コード `0`。手動レビューを促す警告がある場合も含みます。
- 機械的に証明できる整合性の失敗がある場合は終了コード `1`。
- CLI の入力が不正な場合は終了コード `2`。

警告は失敗ではなく、レビューを促すものとして扱ってください。意味的な正確さ、ビジネス上の意味、タスクの完了、リリースの承認は、人間またはワークフローの担当者が判断します。

## 使用場面

依頼が十分に広く、適切なガバナンス機能を選ぶこと自体が作業の一部である場合に、このルーターを使用します。ADR やリグレッションを直接求められた場合は、このスキルを経由せずに、専門のスキルを呼び出してください。

## 仕組み

1. リポジトリの既存の指示とドキュメントの領域を把握する。
2. 成果物ロール契約を通じて論理的なロールを解決する。
3. ルーティング表から、最小限で一致する機能を 1 つ選択する。
4. 決定論的な監査が求められた場合は、有用な範囲で最も狭いスコープを実行する。
5. プロジェクトの状態を変更せずに、失敗、警告、担当の空白を報告する。

## 例

- 「長期にわたるプロジェクトドキュメントを整理して」は `living-docs-governance` にルーティングされます。
- 「PostgreSQL を選んだ理由を記録して」は `architecture-decision-records` にルーティングされます。
- 「ドキュメントのリンクと ADR インデックスが壊れていないか確認して」は、同梱の監査を `--scope artifacts` で 1 回、続いて `--scope adr` で 1 回実行します。
- 「マイグレーションは完了した?」という問いは、ドキュメントだけからは回答しません。完了を所有するのは Issue、証跡を提供するのはテスト、マージの承認を所有するのはメンテナーです。

## 境界

- タスクの担当、スケジュール、試行、完了は Issue トラッカーで管理します。
- 安定したインターフェースの事実は、リポジトリの契約ソースで管理します。
- ドキュメントは、実行可能な指示ではなく、証跡およびナビゲーションとして扱います。
- pre-commit フックなど、リポジトリの統制を回避する方法をユーザーに教えないでください。
- この読み取り専用の基盤に、アーカイブやインデックスの変更を追加しないでください。
