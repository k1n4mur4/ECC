# ベンチマーク最適化ループ

まずユーザーが達成したいことから始め、そのうえでベンチマークを選びます。正確性や品質を改善したいという要望が、速度の最適化になるとは限りません。
「20 倍高速にして」や「再帰的な最適化を 50 回試して」といった要望であっても、有界で測定可能なループが必要です。

## 使用タイミング

反復的な測定比較を必要とする、目標駆動の実装変更に使用します。あるいは、そのようなタスクのためにベンチマークと計画を確立する場合に使用します。単発の修正には既存の十分な回帰チェックを再利用し、理由なく探索ループを追加しないでください。

## ツール要件

ホストが既に許可している Read、Write、Edit、Bash、Grep、Glob ツール、またはそれらに相当するものを使用します。このワークフローを読み込んでも、ツールが付与されたり、既存の権限が拡張されたりすることはありません。

## 必須のベースライン

以下が揃うまで最適化しないでください。

- ユーザーのタスク、最適化対象の操作、望ましい成果
- 成功のしきい値、および満たし続けなければならない（合格状態を維持すべき）正確性、品質、安全性、動作の制約
- 主要メトリクス、その方向と定義（例: 不一致額、タスク完了率、ルーブリックスコア、実行時間、p95 レイテンシ、行/秒、解決タスクあたりのコスト、メモリ、エラー率）
- 代表的な入力と、独立した期待結果または較正済みのルーブリック
- 再実行に十分な実装、入力、評価器、環境のバージョンを伴う現在のベースライン
- 探索の予算: バリアント数の上限、時間の上限、支出の上限、データへの影響の上限

確認済みの要件と承認は再利用します。重要な成功のしきい値やトレードオフが欠けている場合は、具体的な選択肢を提案し、ユーザーの判断を得てください。ユーザーが非現実的な目標を求めた場合も、その意欲は保ちつつ、ループを有界かつ測定可能にします。計画のみの依頼は計画にとどめます。有料の呼び出し、本番への負荷、デプロイは、既存の承認の境界を維持します。

比較の間、メトリクス、サンプルセット、期待結果、評価器を固定します。期待結果を候補の実装からコピーしてはいけません。ハード制約は集計スコアとは別に評価します。主観的な品質については、受け入れ済みの例に対してルーブリックを較正し、レビュアー間の不一致を記録します。最適化を行うエージェント自身のセルフスコアだけでは、受け入れの証拠になりません。

そのメトリクスがユーザーの成果をなぜ表しているのかを記録します。代理指標は診断に役立つことがありますが、それを改善しただけではユーザーのタスクが改善したことの証明にはなりません。

## ループ

1. ベースラインを測定します。信頼できる過去の証拠は、比較可能な場合に限って再利用します。
2. ユーザーの目標に関連する証拠からギャップを特定します。
3. 各バリアントが 1 つの仮説だけを検証するよう、バリアントを生成します。
4. 同じ入力形状と評価ルールを用い、比較可能な条件下でバリアントを実行します。失敗、タイムアウト、リトライ、およびそれらのコストを記録します。
5. 正確性、その他のハード制約、安全性、再現性を満たさないバリアントを却下します。
6. 合意した目的に照らして、測定結果が最良かつ許容可能なバリアントを昇格させます。
7. 勝ったパスをスクリプト、コマンド、テスト、設定、またはドキュメントとして成文化します。
8. ベースラインと勝者を再実行して差分を確認し、そのうえで、目標達成を宣言する前に、合意した独立した受け入れチェックを実施します。

すべての実行について台帳を保持します。仮説、正確なコマンド、実装とベンチマークのバージョン、ケース数、主要な結果、ハード制約の結果、失敗/リトライ、証拠の保管場所、採用/却下の判断を記録します。失敗はタスク単位の分母に含めたままにします。統計が成功のみを対象としている場合は、失敗率とタイムアウトを併記し、単一の試行と完了したタスク全体を区別してください。

基準を黙って下げるのではなく、実装を最適化します。サンプルや評価器が誤っている場合は、その証拠を文書化します。成功の意味が変わるような改訂にはユーザーの確認が必要です。改訂にはバージョンを付け、ベースラインと候補の両方を改訂後のルールで再実行し、元の証拠は保存します。

## バリアント表

以下の値は説明のための例であり、測定された証拠でもデフォルトの目標でもありません。
速度の目標では、次のようにバリアントを追跡します。

```text
Variant | Hypothesis | Command | Time | Correct? | Notes
baseline | current path | npm run job | 120s | yes | stable
batch-500 | fewer round trips | npm run job -- --batch 500 | 42s | yes | winner
parallel-8 | more workers | npm run job -- --workers 8 | 31s | no | rate limited
```

レポートの正確性という目標では、独立して提供された照合用の合計値を主要な指標として定義できます。実行が速くなっても、誤った合計値が許容されるわけではありません。

```text
Variant | Hypothesis | Critical mismatches | All periods processed? | Decision
baseline | current mapping | 4 | yes | baseline
mapping-fix | handle missing category | 0 | yes | candidate for acceptance
skip-errors | omit failing periods | 0 | no | reject: incomplete task
```

## 再帰的な探索

再帰的な作業やハイパーパラメータの作業では次のようにします。

- すべての実行を台帳に永続化する
- 直前の実行だけでなく、以前に受け入れた勝者と比較する
- 可能であれば、回答の可視性を制御したうえで、独立した受け入れ用ケースを確保しておく。既知のリプレイチェックは回帰の証拠であり、独立した汎化チェックではない
- 受け入れのフィードバックがその後のチューニングに反映された時点で、それらのケースは開発用の証拠として扱い、最終的な受け入れには新たな独立したケースを用意する
- 改善がノイズの範囲内にとどまる場合、正確性やその他のハード制約が満たされない場合、コストが予算を超える場合、あるいは探索が説明できる範囲を超える数の変数を変え始めた場合は探索を停止する。以前に受け入れた勝者を維持し、ギャップを報告する
- 要求された目標が達成されたら、任意の探索を停止する

探索空間が実際に網羅的であった場合を除き、「大域的最適」ではなく「測定結果が最良かつ許容可能なバリアント」といった表現を使用します。独立したケースが利用できない場合は、独立した受け入れを主張せず、その制限を明記してください。

## 昇格ゲート

バリアントは、以下を満たすまで新しいデフォルトにできません。

- 正確性テストとその他すべてのハード制約に合格している
- 目的に対する測定された差分が、再現されているか、説明されている
- 合意した受け入れチェックがユーザーの目標を支持しており、未テストのパスや代理指標のみの結果が明示的に特定されている
- ロールバックが明白である
- 変更がソース管理または永続的なランブックに記録されている
- 最終サマリーに、正確なコマンド、バージョン、測定値、制限が含まれている

ベンチマークの成功、独立した受け入れ、デプロイ後のユーザー成果は、別々に報告します。デプロイが承認されている場合は、プロジェクトのリリースプロセスに従い、デプロイされたバージョンを同じユーザー成果の定義に照らして検証します。そうでない場合は、候補のデプロイ前の状態を報告します。このスキルはスケジューラをインストールせず、リリース権限も付与しません。

## 関連スキルとソース

ホストにインストールされたプロファイルで利用可能な場合は、関連スキルを再利用します。以下の任意の参照は、ECC の正規ソースへリンクしています。

- [benchmark](../benchmark/SKILL.md) はブラウザ/API/ビルドのパフォーマンスのベースラインを収集します。それらの測定が選んだ目標に役立つ場合に再利用します。
- [eval-harness](https://github.com/affaan-m/ECC/blob/main/skills/eval-harness/SKILL.md) はエージェントの能力/回帰の評価と採点手法を提供します。適切な既存の評価器を再利用します。
- [loop-design-check](https://github.com/affaan-m/ECC/blob/main/skills/loop-design-check/SKILL.md) はフィードバックループと暴走防止を設計またはレビューします。このスキルは測定に基づく探索を実施します。
- [benchmark-methodology](https://github.com/affaan-m/ECC/blob/main/skills/benchmark-methodology/SKILL.md) は、実装のバリアントではなく、競合分析のために競合をスコアリングします。
- [ソースとスコープ](../../../../skills/benchmark-optimization-loop/references/sources.md) はこの拡張の出所を記録しています。
