# ML 導入プレイブック

このスキルは、既存のソフトウェアエンジニアリングプロジェクトに機械学習モデルを実装するための適応的な方法論を提供します。ML をどのように調査し、分離し、学習させ、統合するかを構造化することで、従来のソフトウェアエンジニアリングと MLOps の間のギャップを埋めます。

## 起動条件

- ユーザーが既存のコードベースに「ML を追加」または「アルゴリズムを追加」するよう求めたとき。
- ML を使っていないアプリケーションに、新しいモデル(レコメンデーション、分類、予測など)の統合を計画するとき。
- エージェントが ML コンポーネントを適応的に構築、学習、デプロイするためのワークフローを構造化するとき。

## フェーズ 1: 問題の定式化と実現可能性

モデルのコードを書く前に、「なぜ」と「どのように」を明確にします。
- **ヒューリスティックの確認:** 単純なヒューリスティック(正規表現、ルールベースの並べ替えなど)でより早く問題を解決できないかをユーザーに尋ねます。解決できるなら、そこから始めます。
- **指標の定義:** ML モデルが改善しようとしているビジネス指標(クリック率、レイテンシの削減など)を定義します。
- **失敗の許容範囲:** 「悪い」予測とはどのようなものか、そしてシステムがそれをどう扱うべきかを定義します。

## フェーズ 2: データの準備状況

クリーンでアクセス可能なデータがなければ、ML は役に立ちません。
- **データソースの監査:** 学習データがどこにあるかを特定します。稼働中のデータベースか、静的な CSV か、API か。
- **データコントラクト:** 入力データのスキーマを定めます。どの特徴量が必須か。特徴量が欠けている場合はどうなるか。
- **リークの防止:** ユーザーが提案するデータ分割によって、将来の情報が学習セットに意図せず漏れていないことを確認します(例: 時系列データでは時間順に分割する)。

## フェーズ 3: アーキテクチャへの統合と分離

モデルの推論をコアビジネスロジックと密結合させてはいけません。
- **API 境界:** モデルを API エンドポイント(例: `fastapi-patterns` や `django-patterns` を使用)または専用のサービスクラスの背後に置くことを提案します。
- **フォールバック機構:** デフォルトの状態を設計します。モデルの応答に時間がかかりすぎる場合やエラーが発生した場合、システムはハードコードされたルールへ適切にフォールバックしなければなりません。
- **フィーチャーフラグ:** 新しい ML 推論の呼び出しをフィーチャーフラグで囲み、安全に展開(またはロールバック)できるようにします。

## フェーズ 4: モデルの実装と学習

再現性と反復を考慮してコードを構成します。
- **シンプルに始める:** まずベースラインモデル(例: 単純な scikit-learn のロジスティック回帰や、最小限の PyTorch 線形層)を構築します。
- **再現性:** `pytorch-patterns` または同様のベストプラクティスを適用します。乱数シードを固定し、コードをデバイス非依存にし、テンソル/配列の形状を明示的に文書化します。
- **自動化された証拠:** データ変換と推論スキーマのテストを必須とします。ベースラインと比較する評価スクリプトのないモデルは受け入れません。

## フェーズ 5: MLOps への引き継ぎ

ベースラインモデルを統合したら、継続的な運用へ焦点を移します。
- **`mle-workflow` を参照する:** 実験管理、モデルレジストリ、ドリフト検知の整備へとユーザーを導きます。
- **CI/CD:** モデル評価のステップを既存の CI パイプラインに追加し、今後のコミットでモデルの性能が低下しないようにします。

## 反復的なエージェントワークフロー

このプレイブックを用いてユーザーを支援する際、エージェントは次のように進めてください。
1. アーキテクチャを提案する前に、**確認のための質問をして**フェーズ 1 を完了させる。
2. フェーズ 2 で**データコントラクトを起草し**、ユーザーの承認を得る。
3. 学習ループを書く*前に*、フェーズ 3 の**分離用インターフェース(API/サービス)を書く**。
4. フェーズ 4 で、モデルを学習させ成果物を保存する**再現可能なスクリプトを提供する**。
