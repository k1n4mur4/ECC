# ループ設計 + レビュー

> **前提。** LLM はフィードフォワード型のシステムです。プロンプトが入り、トークンが出る。ターンをまたいで「ゴールに向けて舵を切る」仕組みは組み込まれていません。ゴール指向のシステムのように*振る舞わせる*には、その周囲にフィードバックループを巻きつけます。このスキルは、そのループを正しく**書く**こと、そして暴走しないように**レビューする**ことを支援します。

## 使うとき / 使わないとき

**使うとき:**
- 繰り返し実行されるタスク（write→test、test→fix、fix→verify など）をエージェントに任せたい。
- すでにループがあり、空回りする、ズルをする、誤った答えを最後まで走らせてしまう、といった懸念がある。

**使わないとき:**
- 単発のタスク → そのまま実行する。ループで包まない。
- 単純なタイマー / ポーリング → `/loop` を使う。設計は不要。
- *ループのアーキテクチャをどう配線するか*（パイプライン → DAG、長時間実行からの復旧）→ それは仕組みの層です。`autonomous-loops` / `continuous-agent-loop` を参照してください。**このスキルが扱うのは「ゴールは正しいか、暴走しないか」だけで、仕組みの説明はやり直しません。**

## レッドラインの前提: 2 段階のフィードバック

| レベル | 担当 | 役割 |
|---|---|---|
| **実行**（低位） | 機械 / エージェント | 「文字どおりのゴールからどれだけ離れているか」を測り、それをゼロになるまで詰めていく。機械はここが得意。 |
| **判断**（高位） | **人間** | 「このゴール自体が正しいか、変えるべきか、止めるべきか」を決める。機械は自分のループの外に出てゴールを疑うことができない。 |

> サーモスタットは「26°C からどれだけずれているか」をフィードバックできますが、あなたが熱を出して 28°C にしたいとき、26 が*正しい*目標かどうかは判断できません。ただ 26 に向けてひたすら調整を続けるだけです。**「今日は何度に設定するか」は常に人間の判断です。**
> 判断・承認・最後のスイッチを機械に渡す = 高位のフィードバックを取り除く = 誰も疑っていないゴールに向けて、猛スピードで突き進む = 誤った出力。

## アクション 1 — ループを書く（5 ステップ）

### ステップ 0 · まず引き算: そもそも作るべきか？（4 条件ゲート、1 つでも欠ければ拒否）

① タスクが週 1 回以上繰り返される　② 検証を自動化できる　③ トークン予算に耐えられる　④ エージェントが実際に*実行して結果を見られる*ツールを持っている

どれか 1 つでも欠けたら、**ループを作らない**。手作業か別の方法で行う。
> 多くの人を止めるのは「ループを書けるか」ではなく、「自分のリポジトリはループに値するか」です。ループに値するリポジトリには、突き合わせの基準（ゴールデンサンプル / 上流の合計値）+ テスト + lint ガードがあります。**ループに値しないリポジトリは、ループによって誤りが増幅されるだけです。**

### ステップ 1 · *機械判定可能な*ゴールを定義する（難所 — ループの生死はここで決まる）

ループ全体は、比較器の「もう終わったか？」に乗っています。**比較器が機能するのは、終了条件を機械が yes/no で判定できる場合だけです。**

- 悪い例: 曖昧（「良くして」「もっと鋭く書いて」）→ 比較器が判定できない → 永遠に通らない（リトライで詰まる）か、推測する（ランダムに通す / ブロックする）。
- 良い例: 判定可能（「96 個のユニットテストがすべて green かつ変更リストが生成されている」「module-02 のフィールドが埋まり、pytest が通り、ビジネスロジックに手が入っていない」）→ 1 回のチェックで決着がつき、ループはきれいに収束する。

**5 点ゴールフレームワーク:**
1. **完了基準が機械で検証可能である。**
2. **完了基準と併せて境界条件を定義する**（「やってはいけないこと」）— 反 Goodhart。境界がないことは、ズルをする許可証になる。
3. **失敗時のフォールバックがある** — リトライ上限 N + 超過したら人間にエスカレーション。
4. **ゴールが階層化されている。**
5. **完了基準は表明よりも突き合わせを優先する** — 自分の表明より先に、外部の事実（ゴールデンサンプル / 上流の合計値 / 財務の突き合わせ / プラットフォームのバックオフィスの数値）に基準を置く。「全テスト合格」は抜け道が作れる（assert を緩める、モックを偽装する、例外を握りつぶす）が、「基準との差分 < 0.01」は作れない。

> **セルフチェック:** そのドメインを知らない人にゴールを読み上げて、コマンドを 1 つ実行するだけで終わったかどうか判断できるか？ できないなら、判定可能性が足りません。戻ってください。

### ステップ 2 · ループの種類を選ぶ

| タスク | ループの種類（サイバネティクス） | 停止の仕方 |
|---|---|---|
| 明確な「完了」テストがある（完了まで書く / 画像のバッチを処理する） | **サーボ**（`/goal` 型の閉ループ） | ゴールに到達したら停止 |
| 終点がなく、ある状態を維持し続ける必要がある（在庫アラート / 定期ヘルスチェック） | **レギュレータ**（`/loop` 型のサーモスタット） | 停止しない。変化があったときだけ動く（不感帯でノイズを抑制） |
| 定期的にサンプリングし、条件で停止する（CI が green になるまで PR を見張る） | **出口付きレギュレータ** | 出口条件が成立したら停止 |
| 「何かを時間どおりに確実に起こす」必要がある | 上記を `/schedule` で包む | cron が起動する |

> 目安: 明確な「完了」テストがある → サーボ。維持し続ける必要があり終点がない → レギュレータ。「時間どおりに起こす」必要がある → レギュレータを schedule で包む。

### ステップ 3 · 骨格を選ぶ

**保守型（既存のものを手入れする）→ ドキュメント駆動のディスパッチ。**
ループは「固定のチェックをタイマーで実行する」ものではなく、**「タイマーでドキュメントを読み、ドキュメントが変わったときだけディスパッチする」**ものです。ドキュメントがタスクキュー + 状態機械 + 人間とのインターフェースになります。
3 つの規律: ① 問題の列は人間だけが書き、結果の列はループだけが書く。**状態は一方向に進み、決して巻き戻らない**。② **終了コードが最終である**（スクリプトが exit 1 と言うなら、スクリプトが勝つ）。③ 状態は「検証待ち」までしか進めない — **「完了」のセルは人間だけが切り替える。** ループは作業者であり、検収担当ではない。

**新規構築型（ゼロから作る）→ plan / build / judge の 3 つの役割。**

| 役割 | やること | 要点 |
|---|---|---|
| **Plan** | ゴールを仕様 + **判定可能な受け入れ条件**に分解する | 受け入れ条件はスクリプトで判定できること |
| **Build** | 仕様に従って書く | **受け入れ条件を変更してはならない** |
| **Judge** | 受け入れを**独立して**実行する。合格 → 停止、不合格 → 失敗理由を添えて Build に戻す | **独立 + 決定論的** |

3 つの鉄則（すべて judge に賭ける）: ① **judge は独立していなければならない** — Build と同じエージェントではないこと（自分の宿題の採点は必ず甘くなる）。② **決定論的なルール** — pytest / 突き合わせの差分 / 型チェック / diff であり、「正しそう」ではない。③ **Build は合格するために受け入れ条件を編集してはならない。** リトライに 3 回失敗したら人間にエスカレーションする。

### ステップ 4 · ダンピングを加える（振動 / 暴走への対策）

リトライ上限、ハードストップ、人間による最後のスイッチ操作がダンピングです。**ダンピングのない負のフィードバックは振動します**（Ralph-Wiggum ループ: その場で空回りしてトークンを燃やす）。

### ステップ 5 · 3 段階で着地させる（初日から完全自動にしない）

① **まず手動で 1 回実行する**（「judge がどう判定するか」を正確に言語化せざるを得なくなる）→ ② スキル / Claude Code のサブエージェントとして固める（メインの Claude がループし、plan/build/judge をディスパッチする）→ ③ cron に掛けて完全自動化する。

## アクション 2 — ループをレビューする（チェックリスト = 5 つの失敗モード）

> ループを各行に通してください。**1 つでも該当すれば、このループは誤作動します。差し戻してください。** この 5 つは負の経験（gotcha）であり、正のルールより価値があります。

| # | 失敗モード（どう壊れるか） | レビューの問い（該当 = 赤） | 抗体 |
|---|---|---|---|
| 1 | ゴールが正論の決まり文句 → **空回りして金を燃やす** | 終了条件を機械が yes/no で判定できるか？ それとも「うまく管理する / 良くする」か？ | 判定可能な結果条件に置き換える（アクション 1・ステップ 1） |
| 2 | 「検証」が「問題なさそうか確認する」と書かれている → **エージェントが自信満々に問題なしと言って停止する** | judge は被告本人か？ 検証は「正しそう」に基づくのか、決定論的なルールに基づくのか？ | 突き合わせ + 終了コードのルール + 独立した judge |
| 3 | （最悪）「全テスト合格」だけでゲートしている → **エージェントがテストを削除する** | 境界（「やってはいけないこと」）はあるか？ それとも完了基準だけか？ | 完了基準 **+ 境界**をセットにする（Goodhart への抗体） |
| 4 | エージェントが実行中に質問することを当てにしている → **質問しない。誤った答えを最後まで走らせる** | 「実行時に初めて確認する」ポイントはあるか？ | **確認事項はすべて前倒しする**。起動前に 1 回で決着させる |
| 5 | 肥大化した CLAUDE.md + 古いメモリ → **ループが速いほど誤りが増える** | 依存するドキュメント / メモリは新鮮か？ 誰が保守するのか？ | 階層化したメモリ + 定期的な lint |

**加えて 3 つのレッドライン（1 つでも破れば自動化は許されない）:**
- **判断は人間に残す。** 受け入れ / 「完了」のセルは人間が切り替える。ループは検収担当ではない。
- **責任は移転しない。** 失敗が許されないもの（誤った PR をマージする / 誤ったものを公開する / 資金を誤配分する）→ **権限を自動的に渡さない。**
- **直感に反する警告。** ループが「自己改善する / 自分のルールを書き換える」ものであるほど、**人間のレビューはより厳格に必要になる**（ルールが何に書き換わったかを見るため）— 緩くなるのではない。機械は速すぎて事後に阻止できないため、人間の判断は事後のパッチではなく、**行動の前**（ハードゲート）に置く必要がある。

## 実践例 — 「夜間 green キーパー」ループのレビュー

毎晩実行され、失敗しているテストを修正するループが欲しいとします。

- **素朴なゴール:** 「全テストを合格させる。」→ ステップ 1 のセルフチェックに失敗: これは失敗モード #3 の餌です。
- **判定可能なゴール（修正後）:** 「全テストが green **かつ**テストファイルが削除・弱体化されていない **かつ**カバレッジが下がっていない **かつ**変更リストが生成されている。」境界が完了基準と併せて定義されました。
- **種類:** リトライ上限 3 のサーボ（ステップ 2 + ステップ 4）。
- **骨格:** plan/build/judge — **judge は独立して実行される CI** であり、修正を行うエージェントでは決してない（ステップ 3）。

ここで**レビューチェックリスト**を通すと、素朴な版が見逃していたものを捕捉できます。
- **#3 該当** → 素朴な「全テスト合格」では、エージェントが失敗するテストを削除して「勝つ」ことができる。境界「テストファイルを削除・弱体化しない」で修正。
- **#2 該当** → 修正を行うエージェントが自分の修正も判定すると、自分を合格させてしまう。「judge = 独立した CI、決定論的」で修正。
- **#4 該当** → 修正方法が曖昧なとき、エージェントは午前 2 時に手を止めて質問したりしない。推測をコミットする。前倒しで修正: 曖昧な修正は推測せず、人間に残す。
- **レッドライン** → ループは PR を開くが**自動マージはしない**。最後のスイッチは人間が入れる（責任は移転しない）。

素朴なループとレビュー済みのループの違いは 4 行の制約だけであり、それが「テストスイートが削除された状態で目覚める」か「きれいな PR で目覚める」かの違いです。

## 一行の締めくくり

> ループを書く難しさは「ループを書けるか」ではなく、**機械が突き合わせできるゴールを定義すること**にあります — 判定可能で、境界があり、突き合わせに基づくこと。制御器は決定論的で外部のものでなければなりません。判断と基準は人間に残します。システムはエントロピーに向かうので、保守してください。
> **ループは、すでにきちんと考え抜いた人にしか報いません。ループに考えてもらうことを当てにすれば、ループは喜んで間違った考えを、あなたと一緒に、大規模に考えてくれます。**

> 系譜: 判断 / 実行の分離とレッドラインについては Wiener の 2 段階フィードバック（*The Human Use of Human Beings*、1950）。plan/build/judge パターンは Anatoli の *Loops explained* と Addy の *Loop Engineering* から。
> 仕組みの層（ループのアーキテクチャの配線方法）: `autonomous-loops` / `continuous-agent-loop` を参照してください。このスキルは仕組みを再実装せず、ゴール定義と暴走防止のみを扱います。
