# モジュールガバナンス

モジュールレベルの作業ルールを、既存のドメイン言語、契約、意思決定に接続します。
これはオーケストレーション用のスキルであり、2つ目の DDD 方法論でも、ドキュメントの自動生成ツールでもありません。

## 有効化するタイミング

- ユーザーが新しい業務モジュールの実装を依頼したとき（このスキルの名前を挙げる必要はありません）。
- ユーザーが既存モジュールのドキュメント化、または確定した責務変更の反映を依頼したとき。
- 承認済みのモジュール変更に、ローカルな指示と正規の知識へのポインタが必要なとき。

通常のバグ、スタイリングの変更、境界が変わらない内部リファクタリング、親の規約をそのまま継承するだけの新しいディレクトリや UI コンポーネントでは、セットアップを開始しないでください。設計議論や監査のみの場合は、ファイルを作成せずに調査して報告します。意図に基づく選択はバックグラウンドのフックではありません。また、無関係なコード、コミット、プッシュ、業務上の選択を許可するものでもありません。

## 仕組み

### 1. ドキュメントを作成する前に境界を見つける

該当するプロジェクトおよび上位階層のハーネス指示、既存のマップ、要件、関連コード、契約を読みます。モジュールの責務、非責務、状態の所有権、実際の利用者を特定します。ディレクトリ名だけでは境界づけられたコンテキストは確立されません。重要な曖昧さは、業務ルールを創作せずに明示してください。

既存の境界を変更する場合は、最初に `change-impact` を使用します。その読み取り専用と承認に関する制約は引き続き適用されます。無関係な開発ワークフローを実行しないでください。

### 2. プロジェクト全体のルールとローカルルールを分離する

プロジェクトレベルの指示ソースは、全体の制約、モジュールのナビゲーション、モジュール間の連携を所有します。ローカルの `AGENTS.md` が所有するのは、モジュール固有の追加制約（責務、状態の所有権、公開インターフェースへのポインタ、検証の入口）のみです。ローカルルールでプロジェクト全体の制約を免除することはできません。

確立済みの `CLAUDE.md` やその他の有効なハーネスの仕組みを再利用し、名称変更を強制したり、2つのコピーを維持したりしないでください。親の指示がすでにそのモジュールをカバーしていて、ローカルルールに不足がない場合は、そのソースへリンクし、冗長なローカルファイルを作成しないでください。既存の明示的なローカルエントリポイントの要件には従います。ハーネスがネストされたすべての指示ファイルを自動的に読み込むと主張してはいけません。

### 3. 既存の知識オーナーを再利用する

| 情報 | 既存の ECC オーナー |
|---|---|
| 安定した用語と概念間の関係 | `context-and-decisions`（既存の用語集またはコンテキストの役割を使用） |
| 元に戻しにくい意思決定とその根拠 | `architecture-decision-records`（既存のコンテキスト引き継ぎ経由） |
| 境界をまたぐ機械的に検証可能なインターフェース | `contract-first` |
| ドキュメントのナビゲーションとライフサイクル | `living-docs-governance` |
| 影響を受ける利用者と境界変更の証拠 | `change-impact` |

作業に必要になった時点で該当するスキルを読み込み、その方法論をここで重複させないでください。用語は AGENTS ではなく、関連する既存の `CONTEXT.md` またはそれに相当するものに記載します。同じ業務コンテキスト内のフロントエンドとバックエンドは、その用語集を共有できます。UI 固有の作業ルールはローカルに置けますが、ページごとに用語集を作成してはいけません。既存の契約と ADR は、本文をコピーせず参照によって再利用します。

### 4. 承認された記録のみを維持する

ユーザーが依頼したモジュール作業の範囲内で、不足している最小限のローカルルールと確定済みのコンテキスト項目を更新します。影響を受けるナビゲーションとライフサイクルの更新には `living-docs-governance` を使用し、新しいトップレベル成果物には承認が必要という同スキルの要件を維持します。2ファイルを揃えるという要件を満たすためだけに空のファイルを作成しないでください。実装がまだ存在しない場合は、その境界を「確定した設計、コード未検証」と明記し、文章だけでドキュメントとコードの整合性を宣言しないでください。

### 5. 意味とリンクの両方を検証する

主張されているすべてのオーナー、インターフェース、制約を、コード、正規の契約、実行可能な証拠と照合します。矛盾は所有者が解決できるように報告し、偶発的な実装に合わせるためだけにルールを書き換えないでください。

相対リンクは、ターミナルの作業ディレクトリではなく、**参照元の各ドキュメントのディレクトリ**を基準に解決します。インストール済みの `docs-governance` スキルのパスを解決し、その既存の読み取り専用リンクチェックを合意済みの検証ステップとして実行します。

```bash
python3 <docs-governance-skill>/scripts/audit-docs.py --root <repository> --scope modules --module <module-directory>
```

監査が、変更されたローカル指示、コンテキスト、ナビゲーションをスキャンしたことを確認し、リンクの結果と終了コードを確認します。壊れた参照は修正して再実行し、空のリンク先を作成しないでください。スクリプトが利用できない場合や、対象が除外されている場合は、その対象を未検証として報告します。業務テストに合格してもリンクが正しいことの証明にはならず、同名の既存ファイルが誤った知識オーナーである可能性もあります。

## 例

- **「在庫モジュールを実装して」**: 既存の境界を調査し、本当に新しい制約に対してのみローカルルールを追加します。ドメイン用語集と API 契約を再利用し、既存のナビゲーションからそれらへリンクし、コードと参照元基準の相対リンクを検証します。
- **「決済は別モジュールにすべきですか?」**: ファイルを書き込まず、また議論を実装の承認とみなさずに、境界の選択肢と根拠を説明します。
- **「在庫バッジの色を直して」**: 該当する指示を読み、依頼された UI の挙動を修正します。AGENTS、CONTEXT、ADR のドキュメントは生成しません。
- **「モジュールのドキュメントを監査して」**: 既存の読み取り専用の監査と意味的なレビューを使用します。ローカルファイルがないこと自体は、それを作成する許可にはなりません。

## アンチパターン

- すべてのディレクトリやフロントエンドのページに AGENTS/CONTEXT のペアを必須とすること。
- 全体の制約、用語集の定義、契約、ADR の根拠を重複させること。
- ドキュメントのチェックを、業務実装が完了した証拠として扱うこと。
- 実際のハーネス連携なしに、フックをインストールしたり、ネストされたファイルの自動読み込みを主張したりすること。

## 成果物

正規の記録のパス、そのプロジェクト／モジュールのスコープ、実際の変更、検証の証拠、未解決のオーナーシップに関する問題を報告します。モジュールガバナンスが提供するのは作業ルールと知識への入口であり、DDD への完全な移行ではありません。
