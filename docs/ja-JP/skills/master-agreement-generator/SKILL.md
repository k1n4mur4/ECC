# Master Agreement Generator

マスターテンプレートは 1 つ、取引先ごとの小さなスペックも 1 つ、ドラフトのビルドステップも 1 つです。
ジェネレーターは、完成済みのテンプレートから生成した文書を含め、出力に常に **DRAFT** と表示します。
変換が成功したことが証明するのは成果物が生成されたことだけであり、法的な完全性、契約締結の権限、
送付や署名の準備が整っていることは証明しません。
締結済みの契約が、指定された案件を通知によって追加することを認めている場合があります。
Schedule A ワークフローを使用する前に、その権限が確立されていなければなりません。

## 使用するタイミング

- 枠組み契約（NDA、紹介料またはソーシング手数料、回避禁止、基本サービス契約）を、同じ条件と少数の
  当事者固有フィールドで多数の取引先に発行する場合。
- 案件が時間とともに追加され、案件ごとの契約書の作り直しがボトルネックになっている場合。
- 文書を、追跡されたソースから再現可能で、差分を取れ、手作業の編集がない状態で作成する必要がある場合。
- 署名フィールドが自動化によって配置され、安定したページレイアウトが必要な場合。

## 仕組み

### テンプレート

`{{PLACEHOLDER}}` フィールドを持つ単一の Markdown テンプレートです。当事者固有の値はすべてプレースホルダーで、
それ以外は固定のテキストです。スケルトンは
[references/master-template.example.md](../../../../skills/master-agreement-generator/references/master-template.example.md) にあります。
その汎用的な文を、弁護士が承認した条項に置き換えてください。

リファレンススクリプトが埋めるプレースホルダー:

| プレースホルダー | ソース |
| --- | --- |
| `{{DATE}}` | `spec.date`、デフォルトは今日 |
| `{{CP_SHORT}}` | `spec.short` |
| `{{CP_LEGAL}}`, `{{CP_JURIS}}`, `{{CP_ADDR}}` | スペックのフィールド。取引先が署名時に記入する場合は空行 |
| `{{ROLE_CLAUSE}}`, `{{FEE_TITLE}}`, `{{FEE_CLAUSE}}` | `spec.role` により役割テーブルから選択 |
| `{{SCHEDULE_ROWS}}` | `spec.schedule`、または「署名時点でエントリなし」の 1 行 |
| `{{SUPPLEMENT_CLAUSE}}` | `spec.supplement`。末尾に区切りを付けて出力、または空 |
| `{{CP_SIGBLOCK}}`, `{{CP_SIGNER}}`, `{{CP_TITLE}}`, `{{CP_EMAIL}}` | 署名ブロックのフィールド。不明な場合は空欄 |

### スペック

取引先ごとに 1 つの JSON ファイルを用意します:

```json
{
  "file": "AcmeSupplier",
  "short": "Acme",
  "role": "supplier",
  "legal": "Acme Compute Ltd",
  "juris": "England and Wales company",
  "addr": "1 Example Street, London",
  "signer": "A. Person",
  "title": "Director",
  "email": "signer@example.com",
  "schedule": [["1", "2026-09-01", "Lot A (16 nodes)", "introducer", "12 months", "standard"]],
  "supplement": "the Data Processing Addendum dated 2026-09-01"
}
```

ドラフトに必須なのは `file`、`short`、`role` のみです。署名関連のフィールドが欠けている場合は、
レビューと記入のために空行として出力されます。
[references/spec.example.json](../../../../skills/master-agreement-generator/references/spec.example.json) を参照してください。

`file` は空でない、移植可能なファイル名でなければなりません（例: `AcmeSupplier` や `Acme Supplier`）。
ディレクトリ成分を含めてはいけません。ビルダーは、いずれかのパス区切り文字、ドライブ/UNC 構文、制御文字、
Windows の予約済み句読点やデバイス名、末尾のドットやスペースを拒否します。
無効な名前は、サニタイズや名前変更を行わず、出力の作成や pandoc の呼び出しより前に拒否されます。

`schedule` を省略するか `[]` を指定すると、「署名時点でエントリなし」のプレースホルダーになります。
それ以外の場合、指定するスケジュールは、6 セルの配列を要素とする密な配列でなければならず、順序は
番号、日付、保護対象の取引先またはロット、役割、条件、手数料です。各セルは有効な Unicode 文字列か
有限の数値でなければなりません。意図的な空欄には空文字列を使用できます。
null、真偽値、オブジェクト、ネストしたセル配列、欠落したセル、有限でない数値は、成果物の書き込みや
pandoc の動作より前に、行とセルのインデックス付きで拒否されます。
対になっていない UTF-16 サロゲートも、UTF-8 出力時に置換されることなく拒否されます。
絵文字などの有効な補助文字は引き続きサポートされます。

セルはプレーンテキストであり、Markdown や HTML ではありません。ビルダーは構文文字をエンコードするため、
リテラルのパイプ、バックスラッシュ、バッククォート、マークアップは元のフィールド内にとどまります。
CRLF、単独の CR、LF はそれぞれスペースになり、改行前後のテキストは保持されます。
その他の空白とリテラルの句読点は、出力されたセル内でそのまま保持されます。
元のスペックは変更されません。通常の有効なスケジュールは 6 列を維持します。不正な入力が黙って空の
スケジュールに置き換えられることはありません。

### 役割テーブル

`spec.role` は 3 つの文字列を選択します。常設の取り決めの条項、手数料セクションのタイトル、
手数料条項の冒頭です。

| 役割 | 支払者 | 条項の形 |
| --- | --- | --- |
| buyer | 取引先が、紹介された当事者との取引について支払う | 取引先が当社を非独占的に指名し、ソーシングと紹介を行わせる |
| supplier | 取引先が、紹介された当事者との取引について支払う。当社が本人として購入する場合は、スケジュールの条件で契約する | 取引先が、当社および当社が紹介する買い手に対してキャパシティを提供する |
| mutual | 相手方の紹介により成約した側が支払う | 各当事者が紹介でき、成約した側が支払う |

未定義の役割はビルド時に拒否されます。

### ビルド

オペレーターがレビューしたテンプレートとスペックのみを使用してください。Schedule A 以外の通常の
テンプレート置換はマークアップを扱えるものであり、信頼できない文書に対するサニタイザーではありません。
Pandoc は参照されるローカルまたはリモートのリソースを読み込むことがあります。このジェネレーターは
コンバーターのファイルシステムやネットワークへのアクセスをサンドボックス化しません。それらの参照を
確認し、適切に制限した自身の環境で変換を実行してください。対象を絞ったテストは合成コンバーターを使用しており、
実際の DOCX のレイアウトや分離を保証するものではありません。

```sh
node skills/master-agreement-generator/scripts/build-agreement.js \
  skills/master-agreement-generator/references/master-template.example.md \
  specs/AcmeSupplier.json \
  out/
```

スクリプトはプレースホルダーを埋め、スケジュール表を描画し、必須の DRAFT 表示付きで
`out/<file> MASTER.md` を書き出します。デフォルトでは（または `--require-docx` を指定した場合）、
インストール済みの pandoc が空でない通常の `.docx` 成果物を生成することを必須とします。
pandoc がない、変換に失敗した、または出力がない／空の場合は、終了コード 1 を返します。
pandoc の各プローブまたは変換は 10 秒に制限されます。
認識されない、重複した、または競合するフラグは終了コード 2 を返します。

Markdown のみのドラフトを成功させたい場合は、`--markdown-only` を明示的に使用してください。
このモードは pandoc のプローブも呼び出しも行わず、ライブラリからは `docxSkipped: true` を返し、
電子署名ワークフロー用の DOCX は提供しません。ライブラリの呼び出し側は `{ markdownOnly: true }` を
渡さなければなりません。`{ pandoc: false }` だけでは、DOCX 必須の要件を満たせず失敗するようになりました。
結果は常に `documentStatus: 'draft'` を報告します。生成済みの DOCX は、その Markdown を再ビルドする際に
削除され、変換に失敗しても部分的な DOCX は残らないため、以前の成果物が現在の出力になりすますことは
ありません。生成された両ファイルはバージョン管理に含めないでください。テンプレートとスペックがソースです。

締結用コピーのモードはありません。例には、未解決の角括弧付きの作成指示が意図的に含まれています。
`{{PLACEHOLDER}}` トークンを埋めても、それらの法的規定が完成するわけではありません。締結用文書を
準備する前に、完成した条項、当事者の詳細、権限のある署名者、商業条件、文書の正確なバージョンについて、
別途レビューを受けてください。ドラフトと、レビュー済みの締結用コピーは、別々の記録として保存してください。
DOCX への変換が成功しても、アップロード、送付、署名が承認されたことにはなりません。
esign-field-placement の承認ワークフローを参照してください。

両方の出力先は、解決済みの出力ディレクトリの直下の子でなければなりません。いずれかの出力先に既存の
シンボリックリンク（リンク切れのものを含む）がある場合は、DOCX 変換が無効であっても、どちらの成果物も
書き込まれる前に拒否されます。通常のファイルは再ビルドできます。自身が管理する出力ディレクトリを使用して
ください。これらのチェックは、並行して行われる悪意あるファイルシステムの変更に対する分離を提供するもの
ではありません。返される成果物のパスは絶対パスです。

### 署名ページのジオメトリ

テンプレートは本文を OpenXML の改ページで終えるため、互換性のある DOCX レンダラーでは署名ブロックが
新しいページから始まります:

````markdown
```{=openxml}
<w:p><w:r><w:br w:type="page"/></w:r></w:p>
```
````

署名ページの構造（当社のブロック、続いて取引先のブロック。それぞれ By、Name、Title、Email、Date を含む）
は一貫していますが、ページ分割はテキスト、フォント、レンダラー、形式によって変わる可能性があります。
フィールドを配置する前に、レビュー済みの実際の文書とそのページジオメトリを確認してください。
esign-field-placement スキルを参照してください。

### Schedule A 追加ワークフロー

締結済み契約の実際の権限と通知要件を使用してください:

1. 案件の経済性と交渉戦略を、**社内**の交渉／承認チャネルでレビューします。契約上の内容を送る前に、
   コミットメントの承認を得てください。取引先との共有チャネルは社内チャネルではありません。
2. 提案するエントリ、役割、条件、手数料、発効日が、契約の明示的な Schedule A 通知権限の範囲内に
   あることを確認します。常設条件の変更や、その権限を超える変更には、該当する改定手続きが必要です。
   通知が自らの例外を作り出すことはできません。
3. 締結済み契約が認める受領者と通知チャネルに宛てて、承認済みで取引先固有の日付入り通知を作成します。
   有用なビジネス内容を含めてください。保護対象の取引先またはロット、認められた役割、商業条件、
   適用される手数料です。社内マージン、交渉戦略、他の当事者の経済条件、システムトレース、生のエラー、
   社内ファイリング通知は含めないでください。
4. 送付前に、オペレーターの承認を得るため、正確な通知を提出します。operator-approval-loop を参照して
   ください。承認または参加権限がない間は、取引先チャネルでは沈黙を保ってください。承認は、権限のある
   送信者が実際に通知を配信したという証拠とは別物です。
5. 権限のある配信の証拠、発効日、異議があればその内容を、締結済み契約の実際の要件に従って記録します。
   例示の期間はデフォルトではありません。締結済み文書は不変に保ち、追跡対象のスケジュール記録を更新して、
   社内レビュー用の**ドラフトの統合ビュー**を再ビルドし、締結済みバージョンと承認済み通知への参照を
   付けてください。この再ビルドは、署名済みの契約書に代わるものではなく、法的効力を証明するものでも
   ありません。

## 例

### 通知テキスト

説明用のドラフトにすぎません。これらの条件と日付は、締結済み契約が認めており、かつオペレーターが
この受領者宛の通知そのものを承認した場合にのみ使用してください。

```text
Schedule A notice, 2026-09-02
Agreement: Master Agreement dated 2026-08-14 between Us and Acme
Entry 2: Lot B, 8 nodes, region EU-West
Role: introducer
Terms: 6 month term, start no later than 2026-10-01
Fee: standard
This entry takes effect today unless you object within ten business days
with dated written evidence of a prior relationship with the counterparty.
```

### スペックへのエントリ追加

```json
"schedule": [
  ["1", "2026-08-20", "Lot A (16 nodes)", "introducer", "12 months", "standard"],
  ["2", "2026-09-02", "Lot B (8 nodes, EU-West)", "introducer", "6 months", "standard"]
]
```

再ビルドし、ドラフトの Markdown の差分を確認し、統合されたドラフトを、変更されていない締結済み文書および
通知の証拠とともに社内記録に添付してください。

### 取引先が署名時に自身の詳細を記入する場合

ドラフト作成では、スペックから `legal`、`juris`、`addr`、`signer`、`title`、`email` を省略すると、
空行として出力されます。どの詳細を取引先が記入してよいかは、別途レビューされる締結ワークフローで決定し、
実際のフィールドを検証する必要があります。ジェネレーターは電子署名のエンベロープを作成も承認もしません。
