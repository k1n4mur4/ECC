# ドメインコンテキストと意思決定の引き継ぎ

「これらのビジネス用語が何を意味するか」を、「なぜその選択肢が選ばれたか」とは別に管理します。安定した内容が存在しない場合は、空の殻を作成しないでください。

## ドメインコンテキスト成果物: ドメイン言語のみ

用語の説明が繰り返し必要な場合、1 つの用語が複数の意味を持つ場合、または不明確な言葉がモジュール境界の誤りを招く場合は、まずリポジトリに既存の用語集／ドメインモデル文書、または `.governance/docs-map.json` の `context` ロールを再利用します。既存のコンテキストマップが別個のビジネスコンテキストを示している場合は、そのリンクをたどって該当する用語集を参照します。トピックの所有者が不明確な場合は確認します。異なるコンテキストが同じ語を異なる意味で使用することは正当な場合があります。ディレクトリごとに用語集を作成したり、無関係なコンテキスト間で単一の意味を強制したりしないでください。同等のものが存在せず、かつ用語が確定している場合にのみ、`templates/context.example.md` にある既定の `CONTEXT.md` を提案します。その新しい成果物を書き込む前に、作成についてユーザーの明示的な承認を得てください。また、作業は承認されたドキュメント範囲内にとどめてください。ドキュメント更新に対する一般的な許可は、それ自体では新しい成果物の承認にはなりません。承認された範囲内で既存のマップ済み用語集を編集する場合は、新しい成果物の承認は不要です。

記録するのは次のものだけです。

- ドメイン用語と正確な定義
- 中核概念間の関係
- 確認済みの曖昧さと、採用した解釈
- ドメインオーナーによる確認待ちの曖昧さ

実装の詳細、現在の状態、タスクのスケジュール、要件全文、意思決定の根拠、履歴は含めないでください。これらはそれぞれ、コード/MAP、STATUS/Issue トラッカー、Spec、ADR、LOG に保持します。用語は、コード、契約、またはビジネス上の根拠までさかのぼれる必要があります。未確認の項目には `needs confirmation` と記し、推測しないでください。

## 会話の中で言語を洗練させる

これは能動的なモデリングのワークフローであり、他のスキルが読み取るたびに用語集を書き換えることを求めるものではありません。

- **矛盾を指摘する。** ユーザーの表現を用語集と比較します。「キャンセル」がすでに注文全体の取り消しを意味しているのに、リクエストが 1 行だけの取り消しを許可している場合は、その違いを説明してどちらの意味かを尋ねます。用語を黙って再定義しないでください。
- **多義的な概念を分離する。** 「アカウント」という語については、話し手が顧客組織、個人のログイン、請求関係のいずれを指しているかを明確にします。区別される各概念に対して正確な用語を提案します。却下した同義語は、このコンテキストで実際に同じ概念を指す場合にのみ記録します。
- **具体的なシナリオで関係を探る。** たとえば、1 人の顧客が複数のログインを持てるか、注文の一部だけがキャンセルされた場合に請求書はどうなるか、といった質問をします。シナリオは境界を明らかにするための質問であり、新たに作り上げたビジネスルールではありません。
- **主張を根拠と照らし合わせる。** 関連するコード、テスト、契約、既存の記録を確認します。実装が注文全体のキャンセルしか行わない場合は、提案された部分キャンセルルールとの不一致を明示します。コードが示すのは現在の挙動であり、ビジネスオーナーが望む挙動ではありません。どちらが正しいかを自分で決めないでください。
- **確定した用語は定まった時点で記録する。** 承認されたドキュメント編集の範囲内で、すべての定義を終了時まで先送りせず、その時点で既存の用語集を更新します。定義は 1〜2 文にとどめ、必要に応じて出典とコンテキスト固有の避けるべき同義語を添えます。提案された用語に合わせるためだけに、コード、契約、承認済みの意思決定を書き換えないでください。議論のみ、または読み取り専用の作業では、ファイルを書き込まずに提案する文言を提示します。

プロジェクトの既存の用語集の形式を使用します。新規ドキュメントの場合は、[コンテキストテンプレート](../../../../skills/context-and-decisions/templates/context.example.md)がコンパクトな出発点になります。実際の内容がないセクションは省略します。タイムアウトやユーティリティ関数のような一般的なプログラミング用語ではなく、ビジネス固有の概念を含めてください。

## ADR の引き継ぎ: 既存の機能を再利用する

このスキルは、2 つ目の ADR ディレクトリ、採番方式、ライフサイクル、テンプレートを定義しません。意思決定が元に戻しにくく、コンテキストがなければ将来の読者を混乱させ、かつ実際のトレードオフを伴う場合は、次のようにします。

1. `architecture-decision-records` を読み込んで実行し、リポジトリの既存の ADR の場所、形式、および初期化と書き込みに関する明示的な承認ゲートを維持します。
2. 規約が存在しない場合は、そのスキルに最小限で実用的な場所を選ばせます。ここで別のシステムを作成しないでください。
3. 意思決定の本文をコピーするのではなく、`CONTEXT.md`、プロジェクトマップ、または関連する Spec/Issue から ADR へリンクします。
4. 意思決定が承認、置き換え、または非推奨になった場合は、ライブドキュメントのルールに従って、プロジェクト履歴にイベントを追記します。

日常的な実装の詳細、容易に元に戻せる変更、短期間の実験には ADR は不要です。

## アクティベートするタイミング

- ドメイン用語が繰り返し説明し直されている、または曖昧な言葉が実装のずれを引き起こしている。
- プロジェクトに安定したドメイン言語の入口が必要だが、同等のドキュメントがない。
- コンテキストに関する作業で、`architecture-decision-records` に引き継ぐべき永続的な意思決定が見つかった。

通常のバグ修正の中で確立済みの語彙を利用するだけであれば、モデリングセッションや新しいドキュメントは不要です。

## 使用するタイミング

安定したドメイン言語に、根拠に裏付けられた 1 つの置き場所が必要な場合、またはコンテキストに関する作業で、リポジトリの既存の ADR システムに属する元に戻しにくい意思決定が明らかになった場合に、このスキルを使用します。

## 仕組み

1. マップ済みのコンテキストまたは用語集の成果物が存在する場合はそれを再利用します。同等の信頼できる情報源がなく、ユーザーがその新しい成果物の作成を明示的に承認した場合にのみ `CONTEXT.md` を作成します。
2. 確定した定義と関係を記録する前に、矛盾する言葉を指摘し、具体的なエッジケースを探り、主張をコードと契約に照らして確認します。未解決の解釈は、実装やタスクの状態と混ぜずに明示したままにします。
3. 永続的なトレードオフは `architecture-decision-records` に回し、その根拠をコンテキスト文書にコピーするのではなく、結果として作成された ADR にリンクします。
4. スケジュール、ブロッカー、実行状況は既存の Issue トラッカーに保持します。

## 例

- 多義的なビジネス用語を 1 回だけ定義し、その意味を裏付けるコードや契約にリンクする。
- ドメインオーナーが解決するまで、ドメインの解釈を `needs confirmation` としてマークする。
- 永続的なストレージや境界に関する意思決定を既存の ADR ワークフローに引き継ぎ、コンテキスト成果物からリンクする。

## アンチパターン

- 現在のタスク、スケジュール、要件全文、実装の詳細を `CONTEXT.md` にコピーする。
- 体裁を整えるために、空のコンテキストファイルや 2 つ目の ADR システムを作成する。
- 未確認のドメイン解釈を事実として扱う、または ADR の本文をマップやログにコピーする。
- 異なるビジネス概念を同義語として扱って名前を付け替える、または別個のコンテキストを 1 つの普遍的な用語集に押し込める。
- 用語集の更新を実装変更の許可として扱う、またはコードを意図されたビジネスルールの証拠として扱う。

## 関連スキル

- `architecture-decision-records`: 元に戻しにくい意思決定のための唯一の ADR 方法論。
- `living-docs-governance`: プロジェクトマップ、ステータス、履歴のライフサイクル保守。
- `docs-governance`: 機能横断のルーティングとクローズアウトの順序。

## スケジュールとタスクの境界

タスク、ステータス、ブロッカー、スケジュールは、GitHub Issues や Linear などプロジェクトの既存のトラッカーに保持し、それを唯一の信頼できる情報源とします。外部トラッカーが存在せず、プロジェクトが明示的に採用した場合にのみ、ローカルの `.scratch/` を使用します。スケジュールを `CONTEXT.md`、ADR、PROJECT_STATUS、または履歴インデックスデータベースに記載しないでください。
