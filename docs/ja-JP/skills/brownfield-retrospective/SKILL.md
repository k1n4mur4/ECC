# ブラウンフィールド・レトロスペクティブ

ECC なしで構築されたプロジェクトに対して、ECC のエンジニアリングプロセスを後付けで実行します。既存コードベースの任意のスライスを選び、存在するものを監査し、どのようにしてそこに至ったかを再構築し、4 つの軸のギャップ台帳を抽出したうえで、標準の ECC パイプラインを通じて修正を前向きに実行します。

このワークフローはスライスファーストです。リポジトリ全体のオンボーディングを事前に行わなくても役に立ち、すべてのフェーズはディスク上の永続的な成果物から再開できます。途中から始め、過去へさかのぼり、それから前へ進みます。

## 使用するタイミング

- すでに存在し、形が定まっているリポジトリに ECC を導入するとき
- ユーザーが「既存プロジェクトを監査して」「このコードベースをレトロして」「何を見落とした？」と尋ねたとき
- 長い空白期間のあとにコードベースを引き継ぐ、受け継ぐ、または戻ってくるとき
- ユーザーが「なぜこうなっているの？」に続けて「このままでいいの？」と尋ねたとき
- 次の機能をその上に載せる前に、モジュール、機能、サービスの再考が必要なとき
- レガシー領域を前向きに修正するか、書き直すか、文書化したままにするかを決めるとき

## 使用しないケース

- 既存コードのないグリーンフィールドの作業 — `planner` と `tdd-workflow` を直接使用してください
- 再設計ループなしの仕様駆動開発へのオンボーディング — `spec-miner` エージェントが単独で対応します
- リリースの go/no-go を判断する本番準備状況のパス — `production-audit` を使用してください
- セキュリティのみのスイープ — `security-review` を使用してください
- チームのプロセスに関するレトロスペクティブ（スプリントセレモニー）— これはコードベースを監査するものであり、人を対象としません

## ワーキングセット

すべての成果物は、監査対象プロジェクト内の `docs/retro/<slice>/` 配下に書き込まれます。

| ファイル | フェーズ | 目的 |
|------|-------|---------|
| `gap-register.md` | 0-6 | ステートマシン — 境界、`Current phase:` マーカー、および各行。途中から再開するために必要な唯一のファイルです。 |
| `baseline-audit.md` | 1 | レビュアーの指摘事項、テスト/CI のスナップショット、TODO の一覧。 |
| `reconstructed-spec.md` | 2 | コードが現在実際に行っていること（Requirements + Invariants）。 |
| `target-design.md` | 4 | スライスの目標とする形と、修正の順序。 |

さかのぼって補完した意思決定は、`architecture-decision-records` スキルに従って `docs/adr/` に記録します。プロジェクトが OpenSpec を使用している場合、`reconstructed-spec.md` の代わりに、`spec-miner` が生成する `openspec/specs/<capability>/spec.md` を使用することもできます。

## 仕組み

### フェーズ 0 — エントリーポイントを選ぶ

ユーザーが今関心を持っていることから始めます。最初にリポジトリ全体をマッピングしないでください。

次のいずれも有効なスライスです。

| ユーザーのシグナル | スライス |
|-------------|-------|
| ディレクトリ、モジュール、またはサービスを挙げる | そのパスと、その直接の呼び出し元 |
| 機能またはユーザーフローを挙げる | それを実装するファイル（エントリーポイントから辿る） |
| バグ、インシデント、または課題を挙げる | それを引き起こしたコードと、呼び出しチェーンの 1 階層 |
| 依存関係または技術選定を挙げる | それに関わるすべて |
| 何も指定しない | 変更頻度（churn）の高い上位 2〜3 のパス — 提案してユーザーに選んでもらう |

何よりも先に、`gap-register.md` の冒頭に境界を記録します。対象範囲のパス、エントリーポイント、呼び出し元、影響範囲（blast radius）です。スライスの規模はおよそ 15 ファイルまたは 2,000 行を目安とします。ユーザーの選択がそれより大きい場合は、名前付きのサブスライスに分割し、それぞれを独立した作業行として登録します。1 セッションで監査しきれないほど大きなスライスは、決して終わらないスライスです。境界の横に `Current phase:` マーカーを置き、フェーズが完了するたびに更新します。

### フェーズ 1 — 現状監査

現在存在するものを、証拠とともに確立します。まだ何も修正しないでください。

1. スライスを調査します。マニフェストとフレームワークのフィンガープリント、エントリーポイント、テスト構成、CI チェックを確認します（`codebase-onboarding` の調査手順を、境界内に絞って借用します）。
2. スタックに合ったレビュアーを、可能であれば並列で実行します。すべての指摘には `file:line` の参照を付ける必要があります。
   - そのスタック向けの言語レビュアー（`typescript-reviewer`、`python-reviewer`、`go-reviewer` など）
   - `security-reviewer`
   - 握りつぶされたエラーを見つける `silent-failure-hunter`
   - 不変条件が型に符号化されている箇所での `type-design-analyzer`
   - スライスがホットパス上にある場合に限り `performance-optimizer`
3. 現在の状態をスナップショットとして記録します。テスト数とカバレッジ、lint/CI の状態、境界内の `TODO`/`FIXME`/`HACK` の一覧です。

すべてを `baseline-audit.md` に書き込みます。このフェーズ中に修正された指摘事項はベースラインを損ないます — 台帳のために保留してください。

### フェーズ 2 — 後方への再構築

現在の状態から、それを生み出した意思決定へとさかのぼります。

1. 振る舞いの仕様を抽出します。スライスに対して `spec-miner` を実行します。その Requirements（WHEN → THEN）と Invariants が `reconstructed-spec.md` となり、フェーズ 5 のテストの基準となる真実になります。
2. 境界に対する Git の考古学を行います。
   - ディレクトリの履歴には `git log --oneline -- <slice>` を使用します。`--follow` は単一のファイルパスの場合のみ使用します — 履歴の古さ、作者、変更の頻度
   - 最大のコミットと最も多く revert されたコミット — 圧力のもとで設計が変わった箇所
   - 変更頻度のホットスポット — 隣接するファイルよりはるかに頻繁に変更されたファイル
   - 行き止まり — リリースされなかったブランチやスキャフォールディング
3. 意思決定の一覧化: コードに固定された重要な意思決定（スタックとフレームワークの選択、データモデル、境界、エラー戦略、状態管理）を列挙します。それぞれを `docs/adr/`、README、コメントと照合します。記録のない意思決定は、それ自体が既存の思考のギャップです — ここで黙って補完せず、フェーズ 3 で記録してください。
4. 振る舞いが不透明な場合は、意図を推測する前に `code-explorer` を使って実行パスを追跡します。

### フェーズ 3 — ギャップ分析（4 つの軸）

監査と再構築の結果を台帳の行に変換します。ギャップの種類ごとに 1 つの軸を割り当てます。

| 軸 | 問い | ソース |
|------|-----------|---------|
| 思考 | 決定されたが記録されなかったものは何か？どの不変条件がコードの中にだけ存在するか？ | 意思決定の一覧、再構築された仕様 |
| コーディングプラクティス | コードは、ECC が書いたであろう方法とどこで乖離しているか？ | フェーズ 1 の指摘事項、その言語向けの `rules/` パック、テストの裏付けがない仕様項目 |
| 不足している機能 | 初日から作っていれば含まれていたはずで、このスライスには含まれなかったものは何か？ | 境界での入力検証、可観測性、レート制限、冪等性、マイグレーションとロールバック、a11y、i18n、ユーザー向けドキュメント、CI ゲート |
| 技術選定 | 選ばれた技術がコードベースと衝突していないか？古い、重複している、リスクがある、または欠けていないか？ | 依存関係の一覧、Git の考古学、調査 |

台帳の形式（この表がスキルの永続的な成果物です）:

```markdown
| ID | Axis | Gap | Evidence | Forward fix | Severity | Effort | Status |
|----|------|-----|----------|-------------|----------|--------|--------|
| G-001 | practice | Errors swallowed in retry loop | src/api/retry.ts:42 | Propagate + map at boundary | P1 | S | open |
```

- Severity: `P0` はセキュリティ上の露出またはデータ損失、`P1` は正しさ、`P2` はプラクティスと可観測性、`P3` は技術選定とクリーンアップです。
- Effort: `S` は 1 セッション未満、`M` は数セッション、`L` は独自の計画が必要です。
- Status: `open`、`in-progress`、`done`、`wont-fix`。
- すべての行に証拠への参照が必要です。指し示せないギャップは意見にすぎません。

### フェーズ 4 — 再設計 / 再考

台帳を順序付けられた計画に変換します。プロジェクトの既存のタスクと承認の権限に従ってください。台帳はそのシステムにリンクされた監査証跡として保持し、競合する正規のタスク状態を作成しないでください。書き直し、技術の置き換え、マイグレーション、その他の重要な変更の前に、スコープを確認し、プロジェクトが要求する承認を得てください。

1. `P0` と `P1` の行に対して `architect` または `code-architect` を実行し、`target-design.md` を作成します。内容は、スライスの目標とする形、修正の順序、そして動作している振る舞いを守るための明示的な「変更しないもの」リストです。
2. フェーズ 2 で見つかった未文書化の意思決定すべてについて、レトロ ADR を補完します。再構築されたものとして印を付けます（`status: proposed (reconstructed)`、レトロの日付、元の意思決定が記録より前のものであるという注記）。観察された履歴と推測された意図を分け、意思決定を accepted とする前にプロジェクトオーナーに確認してもらいます。補完した ADR を、意思決定時に書かれたものであるかのように提示してはいけません。
3. すべての台帳の行を次のいずれかに分類します。`fix-forward`（その場で修復）、`rewrite`（スライスを置き換え）、`leave-documented`（wont-fix）。`wont-fix` には台帳に理由を記録する必要があります — 理由付きの wont-fix は思考のギャップを閉じますが、理由のないものはギャップを未解決のまま残します。
4. バックログの順序を決めます。まず `P0`、その後は勢いを保つためにクイックウィンと大きな修復を交互に組み合わせます。

### フェーズ 5 — 前向きの実行

標準の ECC パイプラインを通じて台帳を処理します。基本のペースは 1 セッションにつき 1 行です。

```text
planner (scope the row)
  → tdd-guide (failing test first — for a legacy gap the first test
    usually encodes the missing invariant from reconstructed-spec.md)
  → implement
  → code-reviewer
  → security-reviewer (if the row touches input, auth, or data)
  → doc-updater + ADR (if the decision changed)
  → conventional commit
  → mark the register row done
```

- 行が完了するたびに `gap-register.md` のステータスを更新します。永続的な状態は台帳であり、会話ではありません。
- セッションの区切りでは、プロジェクトのメモリ機構（`unified-memory`、コンテキストキャリア）を通じて引き継ぎ、次のセッションが台帳だけから再開できるようにします。

### フェーズ 6 — クロージャと再監査

すべての行が `done` または `wont-fix` になったとき:

1. 同じ境界に対してフェーズ 1 の監査を再実行します。
2. `baseline-audit.md` と差分を取り、`verification-loop` で検証します — 閉じたと主張したギャップは閉じたままでなければなりません。
3. 差分（当時の指摘事項、現在の指摘事項、閉じた行、先送りした行）を `gap-register.md` の末尾に記録します。
4. 再び現れたものは失敗ではなく新しい行になります — 台帳は 1 回で終わるものではなく、ループです。

## 途中からの再開

どのセッションも途中から始められます。まず `docs/retro/<slice>/gap-register.md` を読んでください。

- 台帳が存在し、`in-progress` の行がある → フェーズ 5、その行を完了させます。
- 台帳が存在し、少なくとも 1 行あり、すべての行が閉じている → フェーズ 6。
- 台帳が存在し、open の行があり、進行中のものがない → `Current phase:` マーカーの位置から再開します（トリアージ待ちの台帳があるフェーズ 3、または最初の行を待つバックログがあるフェーズ 4）。
- 台帳はないが `baseline-audit.md` が存在する → フェーズ 2。
- 成果物がまったくない → ユーザーとフェーズ 0 から始めます。

## アンチパターン

- どのスライスよりも前にリポジトリ全体を監査すること — このワークフローは設計上スライスファーストです。
- フェーズ 1〜3 でコードを修正すること — 監査フェーズは台帳を生成するものであり、監査中の編集はベースラインを損ないます。
- 証拠への参照がない台帳の行。
- 理由が記録されていない `wont-fix`。
- 補完した ADR を、同時代の記録であるかのように提示すること。
- フェーズ 6 の再監査を省略すること — クロージャは宣言するものではなく、検証するものです。
