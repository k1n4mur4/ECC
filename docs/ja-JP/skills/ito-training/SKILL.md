# Itô Training

`ito-training` は、Itô コンピュート上でのトレーニングを扱う ECC の正規スキルです。
ECC は独自のトレーナー、スケジューラ、データパイプラインを実行することはなく、
予約、確保、支出も一切行いません。このスキルは `ito-compute` の**完了済み予約**から連鎖して使用します。

## 現在の本番環境の境界

マネージドトレーニングは現時点では利用できません。ECC ブリッジが公開しているのは `login`、`logout`、`auth`、`find`、`status`、および明示的にゲートされた `evals` のみです。
`train` 動詞は存在せず、正規 CLI の `run` 動詞とデスクの `training-run`
バックエンドはいずれもスキャフォールドのままです。ローカルで強制できる保証は、認証情報を扱う正規クライアントを解決または起動する前に、ECC が `train` を拒否することです。

したがって、認証やコマンドの呼び出しの前に停止してください。不足している機能を報告し、呼び出し元のエージェントに制御を戻します。ローカルのトレーナー、SSH ヘルパー、ブラウザのワークフロー、購入エンドポイントで代用してはいけません。

## 必須のエンタイトルメント

トレーニングが実装された場合、最初のゲートはサーバーで検証された完了済み予約です。ハーネスのメモリ、RFQ、見積もり、ノードの IP、SSH アクセスはエンタイトルメントの証明にはなりません。
バックエンドは、認証済みアカウント、予約、GPU トポロジー、リージョン、ファブリック、期間に紐づいた、最新のトレーニング適格性を返さなければなりません。
期限切れ、失効済み、不一致、不完全、またはすでに解放済みの予約は、確認の前にフェイルクローズします。

## 将来の CLI と API の契約

意図されているコマンド名は `train` です。将来の引き渡しは、次と同等でなければなりません。

```sh
ecc ito train \
  --booking <server-verified-booking-id> \
  --manifest <absolute-reviewed-json-file> \
  --confirmation-ref <opaque-non-authorizing-reference> \
  --idempotency-key <stable-retry-key> \
  --json
```

レビュー済みのマニフェストには、モデルサイズとリビジョン、除染（decontamination）の出所を伴うデータ参照、トレーニングターゲット、ポストトレーニングのレシピ、USD での予算上限、チェックポイントポリシー、最大の追加コストを明記しなければなりません。
生の API キー、SSH キー、ノードのパスワード、ベアラートークン、データセットの認証情報は、引数、マニフェスト、ログ、MCP の結果、チャットのいずれにも含めてはいけません。

クライアントは、マニフェストのパスを正規化し、シンボリックリンクを拒否し、リンクをたどらずに通常ファイルを開き、適切な所有権と制限的なパーミッションを要求し、サイズに上限を設け、開いたディスクリプタからバイト列をハッシュ化しなければなりません。
そのダイジェストは、ワークロードを変更する前に、確認に紐づけられたダイジェストと完全に一致しなければなりません。パスのすり替え、ダイジェストの不一致、サイズ超過、変更可能で安全でないファイルは、フェイルクローズします。

ワークロードの作成は ECC ではなく正規 API が担い、`ok`、`live_api_contacted`、`notice`、および `data` または `error` のいずれかを含む構造化 JSON を返さなければなりません。
トレーニングのデータには、安定した予約 ID、実行 ID、マニフェスト ID、冪等性キーと、状態の列挙値を含めなければなりません。エラーには、安定したコードと、シークレットを含まない安全なメッセージを含めなければなりません。

## 確認と実行のゲート

ワークロードを作成する前に、次のすべてを要求します。

1. 正規バックエンドからの最新のエンタイトルメントとトレーニング適格性。
2. レビュー可能な不変のマニフェストと決定的なダイジェスト。
3. アカウント、アクション、マニフェスト、コストに紐づいた、単回使用の個別の確認。有効期限は短く、リプレイ防止が施されていること。CLI 引数が運ぶのは、不透明で権限を持たない確認参照のみとし、サーバーが帯域外でベアラー権限を解決して消費します。
4. 呼び出し側が指定した冪等性キーを、実行とともにアトミックに予約すること。
5. マニフェストの予算上限を含む、サーバー側でのファブリック、キャパシティ、データポリシー、チェックポイントストレージ、コストの検証。

認証は ID であり、ワークロードに対する権限ではありません。ログイン、API キー、見積もり、完了済みの予約が、トレーニングの確認の代わりになることはありません。
検査と計画の生成は、ワークロードを作成してはいけません。キャンセルとクリーンアップは、それぞれ独自のスコープ付き確認と冪等性の境界を持つ、別個の変更操作です。

## ライフサイクルと復旧

本番向けのインターフェースは、同じ正規クライアントがテナントスコープのステータス、ログ、メトリクス、チェックポイント一覧、キャンセル、クリーンアップを公開するまでは未完成です。
すべての操作には、接続タイムアウトと全体のタイムアウトのそれぞれに上限を設けること、失効を考慮したエラー、構造化された出力が必要です。曖昧なトランスポート障害の後は、再試行する前に冪等性キーでステータスを照会してください。最初のレスポンスが失われたというだけの理由で、2 つ目の実行を作成してはいけません。失効した認証情報はポーリングを停止し、ログインを自動的に開始することなく、呼び出し元のエージェントに制御を戻します。

ステージゲートは正直に報告し、失敗した評価ゲートを決して上書きしないでください。クリーンアップは観測可能でなければならず、別個の経済的アクションが明示的に承認されていない限り、基盤となる予約を解放または変更してはいけません。

## 提案されるバックエンドのステージ

これらのステージは、将来のバックエンド（Layer 0.3）を記述したものであり、ECC に存在するコードではありません。

1. データ準備 — マニフェスト、重複排除、評価スイートに対する除染。カスタムデータの安価な事前チェックとして、150M ラダーの判定ジョブを実行します。
2. 並列化と精度 — モデルサイズ、ノード数、ファブリックから選択します。無駄の多い組み合わせは拒否されます。
3. チェックポイントとフォールトトレランス — 非同期 DCP、torchft。検知は 10 分未満、再開は 15 分未満。損失スパイクによる再起動は、人間によるゲートを伴う提案上のアクションです。
4. カリキュラムと評価ゲート — 段階的な事前学習 / 中間学習 / ロングコンテキスト / ポストトレーニング。それぞれに固定の評価バッテリーがあり、ゲートに失敗した実行は停止します。
5. ポストトレーニング — SFT → DPO → RLVR（DAPO の安定化修正を加えた GRPO）。トレーナーとロールアウトを分離し、古さ（staleness）に上限を設けます。

バックエンドはデスクのテレメトリ（グッドプット、中断率、チェックポイント帯域幅）を出力し、デスクがトレーニングブロックを正直に価格付けできるようにします。

上記のすべてのゲートとライフサイクル操作が正規ランタイムに存在するようになるまで、このスキルはフェイルクローズの可用性チェックとドキュメント上の引き渡しにとどまります。
