# レガシースタイルの継承

メタアーキテクチャの 4 つの観点でコードベースの暗黙の規約を走査し、衝突をユーザーと 1 つずつ解消し、合意事項を強制力のある `.ai-style-rules.md` として結晶化することで、レガシープロジェクトにおける AI のコードスタイルドリフトを防止します。言語やフレームワークには一切依存しません。

## 有効化するタイミング

- ユーザーが `/inherit-legacy-style` と入力したとき
- ユーザーが手書きのレガシープロジェクトへの AI 導入に言及したとき
- ユーザーが AI 生成コードが既存のプロジェクト規約から「ドリフト」することを懸念しているとき
- ユーザーがプロジェクトの暗黙のコーディングルールを抽出して明文化したいとき

## 使用場面

レガシープロジェクトのスタイルを維持し、AI 生成コードのスタイルドリフトを防ぎたい場合に、このスキルを使用します。トリガー条件については上記の**有効化するタイミング**を参照してください。

## 前提条件

- Git（推奨。Git を使わないプロジェクトでは、増分モードでファイルのタイムスタンプにフォールバックします）
- プロジェクトルートへの読み取り/書き込み権限（`.ai-style-rules.md` と、必要に応じて `CLAUDE.md` を生成します）

## ワークフロー

### ステップ 0 — モードの自動検出

プロジェクトルートに `.ai-style-rules.md` があるかを、ユーザーに通知せずに確認します。

| ファイルの有無 | モード |
|---|---|
| なし | **ブランチ A — 初回フルスキャン** |
| あり | **ブランチ B — 増分スニッフ** |

モードを 1 行で伝えてそのまま進めます。ユーザーに選択を求めてはいけません。

### ブランチ A — 初回フルスキャン

**1. 規模を測定し、スキャン階層を選ぶ**

```bash
git ls-files | grep -cE '\.(js|ts|jsx|tsx|vue|py|go|rs|java|kt|rb|php|cs|swift|c|cpp|h)$'
```

| 階層 | ソースファイル数 | 戦略 |
|---|---|---|
| Small | ≲ 50 | すべてのソースを精読する |
| Medium | 50–500 | インフラ層は全読み。ビジネス層は観点ごとに 2〜3 件をサンプリングする |
| Large | ≳ 500 | 厳密なサンプリングと予算上限。まず `--stat` の要約を見て、その後に的を絞って読む |

**2. 4 つの観点で走査する**

1. **ファイルの構造（File Anatomy）** — ファイル内の宣言順序（imports → types → メインロジック → ヘルパー → export）
2. **状態と制御フロー（State & Control Flow）** — 非同期状態、ページネーション、フラグの命名規則
3. **インフラ（Infrastructure）** — 横断的なユーティリティ（インターセプター、フォーマッター、ミドルウェア）の置き場所
4. **エラーハンドリング（Error Handling）** — try/catch、グローバルインターセプター、Result 返却のどれを使うか。null チェックの習慣

**3. シグナル閾値によるノイズ低減を適用する**

ユーザーに割り込む前に、シグナルの強さを評価します。

- **弱いシグナル** → 自動抑制: 少数派が 5% 未満かつ件数が 10 未満の場合は、多数派を採用し、少数派は DONTs に入れる
- **強いシグナル** → 問いただす: ほぼ半々に割れている場合、または中核となる観点で意味的な分岐がある場合
- **小規模プロジェクトの例外**: ソースが ≲50 の場合、「3 対 2」は多数派とみなさない → 問いただす

**4. 衝突を 1 つずつ解消する（Grilling Protocol）**

強いシグナルの衝突ごとに、4 つの選択肢を添えて質問をちょうど 1 つだけ提示します。

> Evidence: `pathA` はスタイル X を使い、`pathB` はスタイル Y を使っている
> WARNING: Risk: 両方を混在させるとプロジェクトのスタイルが分断される
> Choose: `1` X に従う  `2` Y に従う  `3` これは進化なのでルールを更新する  `4` 新しいルールがある

ユーザーが回答するまで中断し、その後に次の衝突へ進みます。質問を積み重ねてはいけません。

**5. `.ai-style-rules.md` を生成する**。次の 3 つの必須セクションを含めます。
- **[Golden Files]** — 実在する模範ファイルのパスと、それが何を示しているかの注釈
- **[Naming & State-Control Rules]** — 具体的で検査可能な規約
- **[DONTs]** — 広めてはならないアンチパターン

**6. 永続フックをインストールする**

強制の強度をユーザーに確認します（`AskUserQuestion` を使用）。

| オプション | 仕組み |
|---|---|
| **1** ソフトフック（推奨） | プロジェクトの `CLAUDE.md` に `@.ai-style-rules.md` への参照を書き込む |
| **2** ハードフック | ソフトフックに加えて、`settings.json` に `PreToolUse[Write\|Edit\|MultiEdit]` フックを追加する |
| **3** フックなし | ルールファイルは保持し、ユーザーが手動で参照する |

### ブランチ B — 増分スニッフ

1. 既存の `.ai-style-rules.md` を読み込む。コミットフィンガープリントがあれば、`git diff <last_hash> HEAD --stat` で差分を特定する
2. 最近の Git 変更を読む（`git log -3 --stat` → 疑わしいファイルを必要に応じて確認）
3. 差分が巨大な場合（数百ファイル超）: `--stat` の要約のみとし、最も大きな変更をサンプリングする
4. 新しいコードを記録済みのルールと比較する → 衝突は Grilling Protocol で解消する
5. `.ai-style-rules.md` の末尾に進化ログを追記する（古いルールを上書きしない）

### ターンごとの強制

`.ai-style-rules.md` がコンテキストにある場合（CLAUDE.md 経由で読み込み）、コードを書くすべてのタスクは、推論の流れの冒頭で**準拠宣言**を行い、従う模範ファイルと回避する DONTs を明示しなければなりません。

## 仕組み

このスキルは、`.ai-style-rules.md` の有無によって初回実行か増分実行かを自動で判別します。

- **初回（ブランチ A）** — プロジェクト規模を測定し、4 つのメタアーキテクチャ観点（File Anatomy、State & Control Flow、Infrastructure、Error Handling）でコードベースを走査し、シグナル閾値によるノイズ低減で弱い衝突を抑制し、強いシグナルの衝突をユーザーと 1 つずつ解消し、Golden Files / Naming Rules / DONTs を含む `.ai-style-rules.md` を生成して、任意の強制フックを提案します。
- **増分（ブランチ B）** — 既存のルールを読み込み、最近の Git 差分から新規または衝突するパターンを確認し、見つかった衝突に対して同じ 1 つずつの Grilling Protocol を実行し、既存のルールを上書きせずに進化ログを追記します。
- **ターンごとの強制** — `CLAUDE.md` 経由でフックされている場合、コードを書くすべてのタスクは、従った模範ファイルと回避した DONTs を明示する準拠宣言から始まります。

## 出力仕様

- プロジェクトルートの `.ai-style-rules.md`（ヘッダーにコミットフィンガープリントと規模の階層を含む）
- 必要に応じて、`@.ai-style-rules.md` への参照を含む `CLAUDE.md`
- 進化ログは `### [YYYY-MM-DD] Style Evolution Log` というエントリとして追記

## アンチパターン

- FAIL: 規模の測定ステップを省略してはいけません — 30 ファイルのプロジェクトをサンプリングすると読み足りなくなり、5,000 ファイルのリポジトリをフルスキャンすると破綻します
- FAIL: 複数の衝突に関する質問を一度に積み重ねてはいけません — 問いただすのは厳密に 1 つずつ
- FAIL: 増分モードで古いルールを上書きしてはいけません — 必ず進化ログを追記する
- FAIL: 確認なしに「ハードフック」をデフォルトにしてはいけません — 強制の強度はユーザーが決める
- FAIL: 構文や技術スタックの優劣を判断してはいけません — このスキルが揃えるのはメタアーキテクチャのみ
- FAIL: 模範ファイルのバグをコピーしてはいけません — 構造は再利用し、欠陥は指摘する

## ベストプラクティス

- スキャンの前に、検出したモード（初回か増分か）と規模の階層を 1 行で伝える
- 大規模プロジェクトでは、まず `--stat` の要約を読み、その後に疑わしいファイルへ的を絞って `Read` する
- ノイズはシグナル閾値に任せる — 843 対 8 の命名の偏りは、ユーザーに割り込まずに自動で解決されるべき
- シグナルの強さが判断できないときは、質問する側に倒す
- CLAUDE.md のソフトフック（`@.ai-style-rules.md`）で通常は十分。ハードフックは、ユーザーが機械的な強制を望む場合に限る

## 関連スキル

- `init` — コードベースのドキュメントを含む新しい CLAUDE.md を初期化する
- `code-review` — diff の正確性とスタイルの問題をレビューする
- `simplify` — 再利用と簡素化の機会についてコードをレビューする

## 例

1. **初回のオンボーディング**
   - ユーザー: 「このスタイルを変えずに、古いコードベースへ AI を導入するのを手伝って。」
   - アクション: ブランチ A のフルスキャンを実行 → 規模を測定 → 4 つの観点を走査 → 衝突を問いただす → `.ai-style-rules.md` を生成 → フックの強度（ソフト/ハード/なし）を提案する。

2. **チーム変更後の増分更新**
   - ユーザー: 「新しいモジュールを追加したので、既存のスタイルルールはそのまま維持して。」
   - アクション: ブランチ B の増分スニッフを実行 → Git の差分を記録済みのルールと比較 → 新たな衝突を問いただす → 上書きせずに進化ログを追記する。

3. **CLAUDE.md による DONTs の強制**
   - ユーザー: 「新しいコードがすべてプロジェクトのルールと一貫するようにして。」
   - アクション: ソフトフックをインストール → `.ai-style-rules.md` が毎セッション自動で読み込まれる → コードを書くすべてのタスクは準拠宣言から始まり、模範パターンを再利用して DONTs を回避する。
