# オペレーター承認ループ

外部の相手先とやり取りするエージェントは、自身の判断だけで送信してはならず、社内のオペレーターには常に状況を共有し続ける必要があります。このスキルは次の契約を定義します。すべての外部向けドラフトは義務（obligation）として起票され、オペレーターは正確なテキストに対して決定を下し、配信台帳が実際に送信されたものを証明します。

## 使用するタイミング

- エージェントが共有チャンネル、メール、チャットで顧客、サプライヤー、投資家、パートナー宛ての返信を下書きし、送信前に人間の承認が必要な場合。
- 送信された各メッセージを、正確なドラフトテキスト、承認したオペレーター、決定時刻に結び付ける監査証跡が必要な場合。
- 古い承認が書き換え後のドラフトを送信させてしまった、または 2 つのワーカーが同じ承認済みメッセージを二重に配信してしまった経験がある場合。
- ドラフトが、台帳にすでにある事実を相手先に繰り返し尋ねてしまう場合。

## 仕組み

### オブジェクト

| オブジェクト | 意味 |
| --- | --- |
| Obligation | 相手先に対して負っている 1 件の事項。ステータスは `drafted`、次に `approved` または `rejected`、その後 `sent` へと遷移します。`direction`、`counterparty`、`channel`、`updated_at` エポックを持ちます。 |
| Draft | 正確なドラフトテキスト、そのテキストの sha256、起点の座標（platform、channel、thread、user）、優先度（P0 から P3）を保持するサイドカー行。義務ごとに 1 つで、再起票時に置き換えられます。 |
| Decision | オペレーターによる承認または却下。オペレーター ID、nonce、決定の対象となったドラフトのエポックとともに記録されます。 |
| Approval snapshot | すでに認可された決定ライターが記録する、不変のテキスト、ハッシュ、エポック、宛先。スナップショットがなければディスパッチを許可できません。 |
| Claim | ランダムなトークンと状態を持つ永続的な予約（以下「クレーム」）。義務ごとにアクティブなクレームは最大 1 つです。 |
| Delivery | 1 組の（obligation, decision）に対する 1 回の送信または通知を証明する台帳行。 |

リファレンススキーマは [references/approval-ledger.sql](../../../../skills/operator-approval-loop/references/approval-ledger.sql) にあります。

### ドラフトの起票

1. 入力をクリーンにします。制御文字を除去し、単一行フィールドの空白を圧縮し、長さの上限（draft、summary、context、counterparty）を適用します。空または過大なフィールドは、黙って切り詰めるのではなく拒否します。
2. ベースラインゲート（後述）を実行します。起票が拒否される場合があります。
3. ドラフトテキストを sha256 でハッシュ化します。ハッシュのプレフィックスは summary に入れ、承認パネルがどのテキストを承認しようとしているかを表示できるようにします。
4. アップサートします。同じ（counterparty, channel）に対してオープンな drafted 義務がすでに存在する場合は、ドラフトのサイドカーを置き換え、義務の `updated_at` を進めます。この更新がエポックのローテーションであり、古いエポックに紐付いた決定は新しいテキストを送信させることができなくなります。存在しない場合は、ステータス `drafted` の新しい義務を挿入します。
5. 起票レシートは、設定済みで検証済みの社内オペレーション宛先にのみ送ります。起点がその社内宛先であれば、そこで確認応答を返します。never-silent とは社内への報告を意味し、外部への自動返信を意味しません。ドラフトのハッシュ、承認ステータス、オペレーターの身元、ワークフローのメタデータは、相手先から見えるチャンネルに出さないでください。不明または未分類の起点は静かにしておきます。ダイレクトメッセージが自動的に社内扱いになるわけではありません。

検証済みの社内宛先が利用できない場合は、起票結果を社内のツール結果またはオペレーター画面に保持します。外部または不明な起点へフォールバックしてはなりません。部外者に公開されるツール結果は社内の画面ではありません。

ドラフトの起票は外部への応答を認可するものではありません。ポリシー上許可される確認の質問や中立的な応答は、別個の外部送信の決定であり、counterparty-channel-discipline における既存のメンション、チャンネル、draft-only、frozen、never の制約に従います。社内の承認メタデータを開示してはなりません。

### ベースラインゲート

ドラフトを起票する前に、相手先の現在のベースライン（時系列台帳、契約ストア、または CRM）を照会します。

- 署名済みまたは納品済みの契約が記録されている場合: 証拠と推奨事項を添えて起票を拒否します。署名後に仕様について相手先に尋ねることは、このゲートが防ぐために存在するまさにその失敗です。
- オペレーターによるオーバーライド: `force_despite_signed_contract` を指定すると起票が通り、ドラフトの context に `[BASELINE_OVERRIDE_SIGNED_CONTRACT]` が刻印されます。
- ゲートサービスに到達できない場合: 起票は続行され、context に `[BASELINE_CHECK_UNAVAILABLE]` が刻印されます。パネルにはガードが無効だったことが表示されます。障害によってゲートが黙って無効化されることはありません。
- 事実が利用可能な場合は、最新のいくつかを `[BASELINE FACTS: ...]` のダイジェストとして context に添付し、ドラフトが最新の事実とともに届くようにします。

### 決定

承認パネルには、ステータスが `drafted` で direction が `we_owe_them` の義務が一覧表示されます。承認または却下は、ドラフトのエポック（`draft_updated_ts`）を持つ決定行を書き込み、同じトランザクション内で義務のステータスを切り替えます。エポックが現在の `updated_at` と一致しない決定は古いものであり、何も送信させてはなりません。

すでに認可された承認決定については、同じトランザクションで不変の `obligation_approval_snapshots` 行を挿入します。この行には、決定 ID と義務 ID、現在のドラフトのエポック、正確なテキストとその SHA-256、platform/channel/thread、種別 `draft_sent` が含まれます。決定ライターは書き込み前に認可を確立しなければならず、リファレンスはオペレーターの認証も決定の生成も行いません。自動承認ポリシーはリファレンスによって有効化も拡張もされません。スナップショットのない従来の決定には、明示的な照合または新たな承認が必要です。現在の可変なドラフトから許可をバックフィルしてはなりません。

### 配信

SQLite のリファレンスは [references/approval_claims.py](../../../../skills/operator-approval-loop/references/approval_claims.py) です。これはディスパッチ許可を与えますが、トランスポートを呼び出すことはありません。SQL フィクスチャから初期化済みの既存のローカルリファレンスデータベースを使用してください。このモジュールはスキーマや本番マイグレーションを適用しません。承認レコードを投入できるのは信頼された決定ライターのみです。すべてのライターは外部キーと再帰トリガーを有効にし、スキーマのガードを遵守しなければなりません。データベースへの管理者による改ざんはこのモデルの対象外です。

1. バインドされた承認済みドラフトを発見します。発見は許可ではありません。`claim()` は独自の `BEGIN IMMEDIATE` トランザクションを開き、現在の承認済みエポック、正確なテキスト、計算した SHA-256、完全な宛先をスナップショットに対して検証し、トークンを返す前に一意のクレームを挿入します。競合が発生した場合、ワーカーはトランスポートの前で停止します。完了したレシートは再度クレームできません。
2. `begin_dispatch()` はバインディングを再検証し、トークンを使って `claimed` を `dispatching` にアトミックに変更します。コミット後、競合に勝った呼び出し元だけが正確な `draft_text` と宛先を受け取ります。テキストを再生成したり、トランスポートのために可変なサイドカーを再読み込みしたり、別の試行のためにペイロードを再利用したりしてはなりません。呼び出し元のトランザクション内（ネスト）での呼び出しは拒否されます。許可が後続の呼び出し元のコミットに依存してはならないためです。トランスポートをまたいでデータベーストランザクションが開いたままになることはありません。
3. 成功が確認された結果は `complete()` に渡されます。`complete()` は配信座標をアトミックに記録し、クレームを delivered にし、義務を `sent` に切り替えます。同一の完了は何も起こさず（no-op）、矛盾する座標は失敗します。レシートの UNIQUE キーが重複排除するのはレコードであり、過去の外部への影響ではありません。
4. 例外、タイムアウト、begin-dispatch 後のワーカーの死、またはレシートの永続化の失敗は、ブロックされた試行として残ります。`mark_unknown()` が不確実性を記録します。unknown のクレームは期限切れにならず、再オープンされず、自動再試行されず、その義務に対する別の決定がそれを迂回することも許しません。信頼された呼び出し元は、成功が確認された座標と証拠を添えて `reconcile()` を使用できます。モジュールはその証拠を検証しません。レシートがないことは未配信の証明ではありません。

保証されるのは、承認された決定ごとに自動のディスパッチ試行が 1 回であることであり、外部配信の exactly-once ではありません。begin-dispatch の後、トランスポートの前にクラッシュすると、送信ゼロでクレームが保持されたままになることがあります。unknown の結果を新しい試行のために解放するには、元のエグゼキューターのフェンシングとプロバイダーのセマンティクスの検証が必要になります。このリファレンスは、そのような再試行操作を意図的に提供しません。

| クレームの状態 | 許可される次の状態 |
| --- | --- |
| claimed | dispatching、またはディスパッチ前の cancelled |
| dispatching | delivered または unknown |
| unknown | 信頼された照合を通じてのみ delivered |
| delivered、cancelled | 終端状態。決定キーは再利用できません |

クレームがアクティブな間、データベースのガードは、置き換えを含め、義務、ドラフト、決定への書き込みを凍結します。スナップショットとクレームは消去できません。再起票する前に、クレームされた操作をそのトークンでキャンセルしてください。その後、古いトークンは何も許可しません。ディスパッチが開始された後は、新しい編集や取り消しを照合のために保留します。これは、実行中の操作を呼び戻したふりをするのではなく、変更を直列化するものです。

却下された決定や、ドラフトのサイドカー/スナップショットを持たない従来の行は、この外部ドラフト送信経路に入ることはありません。それらは社内のオペレーター画面に報告し、手動で処理します。社内レシートのフッターは社内に留まります: `approved by <operator> · receipt <decision_id> · draft sha256 <prefix>`。すでに承認された外部向けテキストを、ワークフローのメタデータを追加するために変更してはなりません。

対象を絞ったローカル検証には、プロバイダーや実際のメッセージではなく、一時的なデータベース、別々の接続、模擬の試行カウンターを使用します: `python3 -m unittest discover -s tests/skills -p 'test_approval_delivery_claims.py'`。このテストには、SQLite のシリアライゼーションをサポートする Python 3.11 以上が必要です。リファレンスは標準ライブラリのみを使用します。既存の desk-pattern 契約チェックは、別の互換性チェックとして残ります。

### 時間制限付き自動承認（オプション）

ドラフトは `auto_send_after`（エポック秒）を持つことができます。スイープは、決定がないまま期限が過ぎたドラフトを、オペレーター `auto-ttl` として記録して承認し、その後の配信は通常の経路で進みます。オペレーターの操作は常に優先されます。決定はスイープが見る前にステータスを切り替え、再起票はエポックをローテーションして期限を移動またはクリアします。スイープは書き込みトランザクション内でステータスとエポックを再確認するため、競合は no-op として解決されます。期限のないドラフトは永久にハードゲートされたままです。

### シグナルのリンク

ドラフトは、それが応答するインバウンドの義務を名指しできます（`signal_obligation_id`）。これはレイテンシ測定（インバウンドのシグナルからドラフトされた応答まで）における唯一の事実に即したリンクであり、SLA スキャンがそのインバウンド項目を応答済みとして扱えるようにします。参照された行が存在しない場合は、起票を拒否します。

## 例

### ドラフトを起票する

```text
file_request(
  draft="Thanks, we can hold the slot until Friday. Which start date works?",
  counterparty="acme-supplier",
  context="reply to delivery window question",
  origin_platform="slack", origin_channel="#acme-shared",
  origin_thread="1712345678.000100", priority="P1",
  signal_obligation_id=412)
-> {obligation_id: 431, draft_sha256: "9f2c...", refiled: false}
```

設定済みで検証済みの社内オペレーション宛先には、次のように表示されます:
`Draft filed for approval (P1, sha 9f2c8a1b). Waiting on operator.`
相手先から見える起点チャンネルには、起票通知は届きません。検証済みの社内宛先が利用できない場合、レシートは外部へのフォールバックなしに、社内のツール結果またはオペレーター画面に留まります。

### 方向修正後の再起票

オペレーターがより短いドラフトを求めます。同じ（counterparty, channel）に対して再度起票すると `refiled: true` が返され、サイドカーのテキストとハッシュが変わり、`updated_at` が進みます。古いパネル行でクリックされた承認は古いエポックを持つため、無視されます。

### ゲートによる拒否

```text
DeskApprovalError: baseline gate refused this draft: the ledger shows a
signed contract for 'acme-supplier'. Evidence: master agreement executed
2026-08-14. Recommendation: do not ask. Re-file with
force_despite_signed_contract=true if this is genuinely a new thread.
```

### 社内チャンネルでの配信フッター

```text
Confirmed for Friday, start date 2026-09-08.
approved by operator-a · receipt 118 · draft sha256 9f2c8a1b2d3e4f50
```

## テストすべき不変条件

- 起票レシートは、設定済みで検証済みの社内オペレーションにのみ送られる。起点がその検証済みの社内宛先である場合にのみ、起点もレシートを受け取る。
- 不明な起点は静かなままである。社内宛先が利用できない場合は、外部へのフォールバックなしに、社内のツール結果またはオペレーター画面を使用する。
- 同じ（counterparty, channel）を 2 回起票しても、義務は 1 つ、エポックは 2 つになる。
- 古いエポックを持つ決定は、配信行を生み出さない。
- 同時にクレームを試みる 2 つのワーカーからは、ディスパッチ許可が 1 つしか得られず、敗者がトランスポートを試みることはない。
- unknown の結果とレシート永続化の失敗は、自動再試行を有効にしない。
- 正常完了は、レシートと sent ステータスを 1 つのトランザクションで記録する。
- 変更されたエポック、テキスト、ハッシュ、または宛先では、クレームの取得も開始もできない。
- アクティブなクレームは再起票をブロックする。ディスパッチ前のキャンセルだけがそのホールドを解除できる。
- ゲートが利用不可の場合はマーカーが刻印される。ゲートが署名済みと判定した場合は、force なしでは拒否される。
- auto-ttl は、オペレーターがその後に再起票したテキストに対して発動しない。
