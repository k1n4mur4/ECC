# インテント駆動開発

仕様化を儀式にすることなく、有用な受け入れ基準を作成します。まず利用可能なコンテキストを調査し、
本当に曖昧な点を明らかにし、作業内容とそのリスクに合った検証方法を選びます。

## 有効化するタイミング

- ユーザーが実装前に、機能の明確化、受け入れ基準の定義、変更のリスク低減を求めた場合
- 依頼がセキュリティ、認証、永続データ、マイグレーション、外部 API、またはコンプライアンスに関わる場合
- ユーザーが別のエージェントやチーム向けの引き継ぎ成果物を準備したい場合
- 依頼が曖昧で、期待される結果をまだ観測できない、またはテストできない場合
- ユーザーが `/intent-driven-development` でこのスキルを明示的に呼び出した場合

些細な編集、単純な 1 行修正、進行中のデバッグセッション、コードレビューの依頼、
受け入れ条件がすでに明確な実装依頼では有効化しないでください。

## 仕組み

1. **まずコンテキストを調査する** — 質問をする前に、リポジトリ、ドキュメント、スキーマ、テスト基盤から技術的な事実を読み取ります。一方、プロダクト/ビジネス上の制約は、ユーザーまたはプロダクト成果物だけが提供できるものとして扱います
2. **深さを選ぶ** — リスクの特性に基づいて、Quick Capture（3〜7 件の基準、低〜中程度のリスク）または Full Acceptance Brief（セキュリティ、データ、マイグレーション、システム横断の変更）を選択します
3. **質問は最小限にする** — 推論できず、かつスコープや挙動を大きく変える答えが必要な質問だけを行います
4. **観測可能な基準を書く** — 各 AC-NNN は、開始条件、トリガー、期待される結果、禁止される副作用、検証方法、優先度を記述します。根拠なしに「正しく」や「安全に」といった曖昧な言葉は使いません
5. **続行または引き継ぐ** — 明確でブロッキングリスクのない依頼では、基準を記録して続行します。リスクのある変更では、ブロッカーを提示して確認を待ちます
6. **改訂を扱う** — 実装中にアーキテクチャ上の制約で AC を満たせなくなった場合は、`[revised]` と記し、スコープや検証方法を更新し、リビジョン番号を増やして、変更された基準だけを再提示します

## 例

**Quick Capture — 「ダッシュボードに CSV エクスポートを追加する」**

```
Goal: Authenticated users can download dashboard data as a CSV file.
In scope: Export of currently filtered rows; filename includes date.
Out of scope: Scheduled exports, email delivery, Excel format.
Assumptions: Max row count is under 10k; no PII in exported fields.

AC-001: Export generates file with correct headers
- Scenario: authenticated user, at least one data row visible
- Action: click "Export CSV"
- Expected: browser downloads file with columns [id, name, created_at]
- Must not: expose internal fields or rows belonging to other users
- Verification: automated integration test + manual schema spot-check
- Priority: Required
```

**Full Acceptance Brief のトリガー — 「ユーザー認証を OAuth に移行する」**

認証の変更 + 外部依存 + 既存のセッションデータ → リスクレビュー表、セッション無効化戦略に関するブロッキング決定、
および明示的なロールバック AC を含む Full Brief にします。

**既存仕様のレビュー — ユーザーが PRD を貼り付けた場合**

スキルは、スコープ境界の欠落、検証不能な要件（「システムは高速であること」）、暗黙の前提を探してレビューし、
ディスカバリーをやり直すことなく、修正版または補足の基準を返します。

### 既存 Issue の引き継ぎ例

既存の Issue を引き継ぐ場合は、引き継ぎを準備する前に、元の説明文を
後続のコメントおよび検証済みの証拠と突き合わせて整合させます。
Issue 本文が最新であると決めつけてはいけません。

**架空の Issue:**

- フェーズ A: ブロック中、データベースの承認待ち。
- フェーズ B: 未着手、API コントラクト待ち。

後続のコメントが、フェーズ A が承認チェックに合格したと報告しており、
レビュー記録と成功したテスト結果が添えられています。エージェントは、
この 2 つの証拠がどちらもフェーズ A に該当することを確認します。
フェーズ B には依然として API コントラクトの承認が必要です。

検証済みの進捗は、完了したという主張だけではなく、
確認済みの証拠によって裏付けられていなければなりません。

**整合後の Issue 状態（ドラフト。承認なしには公開しない）:**

- フェーズ A: 完了。検証済みの承認レビュー記録と
  成功したテスト結果によって裏付けられている。
- フェーズ B: 保留。API コントラクトの承認待ち。
- 次のアクション: API コントラクトをレビューして承認する。
- 前提条件: コントラクトとその指定レビュアーを入手する。
- 受け入れチェック: 承認が追跡可能なレビュー記録に残されていることを確認する。

これは提案された Issue の更新であり、承認された編集ではありません。
承認を得た場合にのみ公開し、その後、公開された説明文を読み戻して内容を検証します。

**未検証の主張のバリアント:**

後続のコメントが「フェーズ A は完了」としか述べておらず、
検証可能な証拠がない場合は、フェーズ A の完了を不確定のままにします。
主張を受け入れ済みの結果として扱うのではなく、不足している証拠を記録します。
元のブロッカーを黙って消したり、現在の状態を確認せずに
フェーズ A が依然としてブロック中だと断定したりしてはいけません。

**取得済みと受け入れ済みのバリアント:**

3 つの架空のデータカテゴリを含むタスクでは、
依頼されたすべてのカテゴリを引き継ぎに保持します。

| カテゴリ | 検証済みの状態 | 不足している前提条件/証拠 | 次のアクション | 受け入れチェック |
| --- | --- | --- | --- | --- |
| A | レコードは取得済みだが未受け入れ | 受け入れレビューと検証結果が不足 | 合意済みの基準に照らしてレコードを検証する | 必要なチェックが通り、受け入れが記録される |
| B | ソースが未確立、総数は不明 | 権威あるソースとカバレッジの証拠が不足 | 権威あるソースを特定し、カバレッジを確立する | ソースとレコードの範囲が検証される |
| C | 限定されたサブセットでは 0 件が返った | サブセットのカバレッジとより広い範囲が不明 | サブセットのカバレッジと、より広いデータが存在するかを判定する | カバレッジが検証される。サブセットからグローバルな不在を推論しない |

データの取得成功を、受け入れ済みの作業と同一視してはいけません。
裏付けのない件数や未検証の完了の主張は、
明示的に不明のままにします。

未完了のカテゴリごとに、次のアクション、
不足している前提条件または証拠、および受け入れチェックを特定します。

## 運用ルール

1. ローカルで発見できる技術的事実について尋ねる前に、利用可能なリポジトリ、ドキュメント、Issue、デザイン、
   テストのコンテキストを調査します。
2. プロダクトやビジネス上の制約をコードから推論しないでください。ビジネスルール、コンプライアンスや
   規制上の義務、契約上の SLA、価格、データ保持ポリシー、優先順位付け、対象ユーザーは、
   リポジトリからは読み取れません。ユーザーが提供するか、権威あるプロダクト成果物（PRD、契約書、
   ポリシー文書）に記載されるまで、不明として扱います。これらは、発見された事実ではなく、
   確認が必要な前提として記録します。リポジトリが示すのはシステムが現在どう振る舞うかであり、
   ビジネスがそれに何を求めているかではありません。
3. 回答が必須で、安全に推論できない質問だけを行います。やり取りの無駄を省けるなら、
   短く関連のある質問はまとめます。
4. デフォルトでは実装をブロックしません。ユーザーが十分に明確な変更の実装を依頼した場合は、
   主要な前提と受け入れ基準を簡潔に記録した上で、続行するか、実装ワークフローに引き渡します。
5. 未解決の決定が、重大なセキュリティ露出、データ損失、不可逆なマイグレーション、契約/API の破壊、
   無視できないコスト、または破壊的な外部アクションを引き起こしうる場合に限り、
   続行前にユーザーの明示的な確認を求めます。
6. ユーザーが依頼した場合、またはアクティブなリポジトリのワークフローが明示的に要求する場合を除き、
   受け入れドキュメントをリポジトリに書き込んだり、プロジェクトファイルを変更したり、ブランチを作成したり、
   コミットしたり、別のスキルを呼び出したりしないでください。
7. 自動テストは真実ではなく証拠として扱います。信頼でき、かつ釣り合いが取れる場合は自動化を優先し、
   自動化では結果を確立できない場合は、手動での UX、アクセシビリティ、セキュリティ、法務、
   運用面の検証を認めます。
8. 受け入れ基準、フィクスチャ、例、保存される成果物には、実際のシークレット、認証情報、トークン、
   秘密鍵、個人データ、機微な本番ペイロードを決して含めないでください。
   マスクした値または合成値を使用します。
9. 明示的な承認と、特定された安全な環境がない限り、破壊的なテスト、マイグレーション、セキュリティ
   プローブ、負荷テスト、有料の外部呼び出し、本番/ライブデータに対する操作を実行しないでください。
10. 実装中に発見されたアーキテクチャ、プラットフォーム、または外部の制約により受け入れ基準を満たせない
   場合は、黙って破棄したり回避策で済ませたりしないでください。該当する基準を更新し
   （`[revised]` と記し、制約を明記し、スコープや検証方法を調整）、リビジョン番号を増やして、
   続行する前に変更された基準だけをユーザーに再提示します。改訂がブロッキング決定を変更する場合、
   または安全性や正確性の保証を大きく低下させる場合にのみ、明示的な確認を求めます。

## 深さを選ぶ

最小限で有用な出力を使います。

### Quick Capture

リスクが低〜中程度の、明確だが些細ではない変更に使用します。次を作成します。

- ゴール
- スコープ内 / スコープ外
- 前提
- 検証方法付きの 3〜7 件の受け入れ基準
- ブロッキング質問（ある場合）

運用ルールにあるブロッキングリスクが存在するか、ユーザーが特に仕様を先に求めた場合を除き、
承認のために実装を遅らせないでください。

### Full Acceptance Brief

曖昧な変更、システム横断の変更、セキュリティに敏感な変更、データを変更する変更、マイグレーション、
コンプライアンス、高コストの変更、またはユーザーが引き継ぎ成果物を求めた場合に使用します。
下記のテンプレート全体を作成し、リスクのある実装の前に、未解決のブロッキング決定について確認を求めます。

### 既存仕様のレビュー

ユーザーがすでに PRD、Issue、計画、または受け入れ基準を提供している場合:

1. ディスカバリーをやり直すのではなく、それをレビューします。
2. スコープ境界の欠落、安全でない前提、矛盾、検証不能な要件を特定します。
3. 修正版または補足の基準を返します。

## ワークフロー

### 1. ゴールとリスクを整理する

次を抽出するか、尋ねます。

- ユーザーまたはシステムにとっての観測可能な結果。
- 影響を受けるアクター。
- 主な失敗時の影響。
- 実際に該当するリスク次元: セキュリティ/プライバシー、永続データ、互換性/API、
  マイグレーション、外部依存、コスト、並行性、パフォーマンス、ユーザビリティ/アクセシビリティ。

無関係なリスクについての一般的な質問は避けます。

### 2. コンテキストを発見する

ローカルまたは接続された成果物が利用可能な場合は、必要なものだけを調査します。

- 既存の挙動と、直接関連するファイルやインターフェース。
- リポジトリの規約、プロダクトドキュメント、API コントラクト、データスキーマ、マイグレーション履歴。
- 既存の検証基盤と、現実的なコマンド。
- 外部依存と、それらを単独でテストできるかどうか。

発見した事実は、ユーザーが提供した前提とは別に記録します。コンテキストを調査できない場合は、
何が不明かを述べ、焦点を絞った質問をします。

リポジトリが明らかにするのは技術的な事実、つまりシステムが現在どう振る舞うか、その規約、そしてコントラクトです。
プロダクトやビジネス上の制約、すなわちビジネスルール、コンプライアンスや規制上の義務、契約上の SLA、価格、
データ保持ポリシー、優先順位付け、対象ユーザーは明らかにしません。これらをコードや命名から再構築してはいけません。
ユーザーまたは権威あるプロダクト成果物からのみ取得し、それまでは確認すべき前提として列挙します。

### 3. スコープを定義する

次を明示します。

- ゴール: 意図する結果を述べる 1 文。
- スコープ内: この変更が提供しなければならない挙動。
- スコープ外: 魅力的だが明示的に除外する隣接作業。
- 前提: まだ証明されていない主張。
- ブロッキング決定: 安全性や挙動に大きく影響する未解決の選択。

### 4. 受け入れ基準を書く

`AC-001`、`AC-002` のように番号を付けます。各基準は、観測可能な挙動と適切な検証方法を記述しなければなりません。
基準とテストが 1 対 1 で対応する必要はありません。

該当する各基準には、次を含めます。

- シナリオまたは開始条件。
- アクションまたはトリガー。
- 期待される観測可能な挙動。
- 意味がある場合は、禁止される副作用。
- 検証方法: 自動テスト、統合チェック、手動 UX レビュー、アクセシビリティチェック、
  セキュリティレビュー、運用チェック、またはステークホルダーによる受け入れ。
- 検証がデータ、サービス、コスト、シークレットに影響しうる場合は、環境/安全上の制約。
- 優先度: required、important、または optional。

「正しく」「安全に」「高速」「直感的」「堅牢」といった言葉は、観測可能な証拠を定義するか、
人間によるレビュー判断として記録しない限り、使用しないでください。

### 5. 関連する境界だけを扱う

次のカテゴリを検討しますが、該当するカテゴリだけを含めます。

| カテゴリ | 含める場合 | 代表的な証拠 |
| --- | --- | --- |
| ハッピーパス | ユーザーに見える挙動が新規または変更される | 成功したワークフローまたは状態遷移 |
| バリデーション | 変更が入力を受け付ける | 不正な値や境界値が、変更を加えることなく拒否される |
| 認可/プライバシー | データやアクションにアクセス境界がある | アクセスが拒否され、機微情報が開示されない |
| 永続化/マイグレーション | 保存データやスキーマが変更される | 後方互換な読み取り、マイグレーション、ロールバックまたはバックアップの挙動 |
| 互換性 | 公開 API、ファイル、イベント、クライアントが壊れる可能性がある | 既存のコントラクトまたはフィクスチャが有効なまま |
| 障害回復 | ネットワーク、サービス、または非同期の障害が存在する | 部分的な状態が残らない、または明確なリトライ/縮退動作 |
| 冪等性/並行性 | 繰り返しや同時書き込みが起こりうる | 重複した副作用や無効な最終状態がない |
| パフォーマンス | ユーザーまたはサービスのしきい値が重要である | 定義された測定条件としきい値 |
| UX/アクセシビリティ | 人が結果を操作する | キーボード操作、フィードバック、エラー回復、視覚的/手動レビュー |

### 6. 提示して続行する

- 明確化/仕様化の依頼では、ブリーフを提示し、列挙したブロッカーについてのみ決定を求めます。
- ブロッカーのない実装依頼では、作業の一部として簡潔な基準のサマリーを提示し、実装を続行します。
- 別のエージェントやチームへの引き継ぎでは、要件を勝手に作り出さなくても行動できるだけの
  コンテキストと検証の詳細を含めます。
- ブリーフをファイルに保存するのは、依頼された場合だけです。リポジトリで承認されたパスがあればそれを使い、
  なければ、書き込む前に保存先を尋ねるか、選んだ保存先を明示します。

```markdown
| Criterion | Verification evidence | Status |
| --- | --- | --- |
| AC-001 | <test/check/review command or evidence type> | Pending |
```

## 合格/不合格の例

スキルが、計画の文章ではなく、検証可能なブリーフを実際に作成したかどうかを判断するために使用します。

**不合格の受け入れ基準**

```
AC-001: The export works correctly and is secure.
```

不合格 — 「works correctly」と「secure」は観測可能ではなく、シナリオ、トリガー、期待される結果、
検証方法がなく、起きてはならないことも何も述べられていません。読み手には、
実装がこれを満たしたかどうかを判断できません。

**合格の受け入れ基準**

```
AC-001: Export generates file with correct headers
- Scenario: authenticated user, at least one data row visible
- Action: click "Export CSV"
- Expected: browser downloads file with columns [id, name, created_at]
- Must not: expose internal fields or rows belonging to other users
- Verification: automated integration test + manual schema spot-check
- Priority: Required
```

合格 — 具体的で観測可能な結果、禁止される副作用、明示された検証方法があります。
これを満たしたかどうかについて、2 人の意見が一致するはずです。

**不合格のコンテキスト項目**

```
Discovered facts: Users on the free tier are limited to 100 exports per month.
```

不合格 — ティアごとの上限はビジネスルールです。コードから推論した発見済みの事実として記載してはならず、
ユーザーが提供したプロダクト/ビジネス上の制約に置くか、確認すべき前提として列挙する必要があります。

### 合格/不合格ルーブリック

すべての回答が「はい」である場合にのみ、ブリーフは合格です。1 つでも「いいえ」があれば、返す前に改訂します。

- [ ] 必須の各基準に、シナリオ、観測可能な期待結果、明示された検証方法があるか?
- [ ] すべての曖昧な用語（「correctly」「secure」「fast」「robust」）が、観測可能な証拠に置き換えられているか、人間による判断として明記されているか?
- [ ] プロダクト/ビジネス上の制約が、提供済みまたは前提として列挙されており、コードから黙って推論されたものがないか?
- [ ] スコープが明示され、スコープ外の項目が名指しされているか?
- [ ] ブロッキング決定が、好みではなく、安全性や正確性に実際に影響する選択に限られているか?

## 品質チェック

ブリーフを返す前に、次を確認します。

- ゴールが、実装の選択ではなく結果を記述している。
- スコープ境界と前提が明示されている。
- 必須の各基準が観測可能であるか、人間による判断として明確に示されている。
- セキュリティ、プライバシー、データ、互換性、外部への影響、UX のリスクが、
  関連する場合にのみ検討され、黙って無視されていない。
- 検証方法が、リスクのある操作のための安全な環境を特定している。
- シークレットや本番の機微情報が出力にコピーされていない。
- 正当な理由や依頼なしに、リポジトリの変更や実装ブロックが課されていない。

## 引き継ぎ

別の計画または実装のワークフローが利用可能な場合は、受け入れブリーフまたは基準 ID をそれに渡します。
専用のワークフローがない場合は、ブリーフをそのまま実装の参照資料として提供します。
特定の名前のスキルやツールがインストールされていると想定してはいけません。

既存の Issue については、引き継ぎを準備する前に、Issue 本文と関連する後続のコメントを読みます。
報告された進捗を検証可能な証拠と突き合わせ、完了した作業、未検証の主張、
取得済みだが未受け入れのデータ、残っているブロッカーを区別します。
アクセスできない、または不十分な証拠は、完了と決めつけずに不明として記します。

残りの各フェーズについて、次のアクション、前提条件または不足している証拠、
および受け入れチェックを明示します。承認された変更が明示的に改訂しない限り、
元のスコープを維持します。

Issue の説明文を変更するのは、承認されている場合だけです。承認された編集の後、
公開された説明文を読み戻し、完了した作業、残っているブロッカー、
受け入れ基準が正確に反映されていることを検証します。検証に失敗した場合は、
引き継ぎが成功したと主張せず、不一致を報告します。
