# チームエージェント・オーケストレーション

エージェントを単一のアシスタントではなくチームのように管理する場合に、このスキルを使用します。目的は、チームベース・オーケストレーションを信頼できるものにすることです: 明確な作業項目、明示的なオーナーシップ、エージェントかんばんの状態、ブランチ分離、コントロールペインの可視化、マージゲートを整えます。

## 起動タイミング

- タスクが複数のエージェント、ツール、ハーネス、ブランチ、または worktree にまたがる。
- ユーザーがチームオーケストレーション、エージェントかんばん、スクワッド、コンダクター、コントロールペイン、マネージャー、デスクトップアプリ、Zellij、tmux、Hermes、Devin、Codex、Claude Code、またはマルチエージェント作業に言及している。
- プロジェクトで人とエージェントの間で共有するワークフロー状態が必要である。
- 既存のエージェントのファンアウトが出力は生んでいるものの、マージ可能なプロダクトにならない。

## 運用モデル

すべてのエージェントを、狭い契約を持つチームメイトとして扱います:

- **オーナー**: 作業項目に責任を持つ人またはエージェント。
- **スコープ**: ファイル、ブランチ、ツールの範囲、および触れてはならない領域。
- **状態**: backlog、ready、running、review、blocked、merged、または archived。
- **エビデンス**: テスト、スクリーンショット、ログ、レビューノート、または評価レポート。
- **マージゲート**: 統合を許可する正確な条件。

## エージェントかんばん

作業をセッションをまたいで可視化する必要がある場合に、エージェントかんばんを使用します。

| 列 | 意味 | 完了条件 |
| --- | --- | --- |
| Backlog | 候補の作業項目で、まだ形になっていない | 受け入れ基準が書かれている |
| Ready | 形になっていて割り当て可能 | オーナーとブランチ/worktree が割り当てられている |
| Running | エージェントが積極的に作業中 | 引き継ぎ成果物と変更ファイルが存在する |
| Review | 作業は完了しているが未マージ | テスト、diff レビュー、リスクチェックに合格している |
| Blocked | 外部からの入力が必要、またはゲートに失敗した | ブロッカーにオーナーと次のアクションがある |
| Merged | メインラインに統合済み | PR がマージされた、またはローカルの main が更新された |
| Archived | もはや関連性がない | 理由が記録されている |

各カードは次のスキーマに従う必要があります:

```json
{
  "id": "agent-card-001",
  "title": "Build dynamic workflow skill",
  "owner": "codex",
  "state": "running",
  "branch": "product/dynamic-workflow-team-orchestration",
  "worktree": ".",
  "acceptance": [
    "Skill exists",
    "Tests cover required concepts",
    "Content artifact contains video and article angles"
  ],
  "merge_gate": "lint, focused tests, and catalog check pass",
  "handoff": "path/to/handoff.md"
}
```

## チームベース・オーケストレーションのフロー

1. **ボードを整える**: 曖昧な構想を、オーナーとマージゲートを持つ作業項目に変換します。
2. **実行モードを選ぶ**: 単一エージェント、動的ワークフローモード、dmux/tmux、worktree ファンアウト、または外部のデスクトップオーケストレーターから選びます。
3. **境界を割り当てる**: カード 1 枚につきオーナーは 1 人とし、ファイルスコープを明確にし、インテグレーターなしでの書き込みの重複を避けます。
4. **エージェントを実行する**: 各エージェントは、コードだけでなくエビデンスと引き継ぎノートも書きます。
5. **順番にレビューする**: まずテスト、次に diff レビュー、続いてセキュリティ/リスクチェック、最後にコンテンツ/プロダクトの仕上げを行います。
6. **意図的にマージする**: 1 人のインテグレーターがコンフリクトを解消し、コントロールペインまたはステータス成果物を更新します。
7. **再利用可能なスキルを抽出する**: カードのパターンが繰り返される場合は、`skills/` に昇格させます。

## コントロールペインの要件

チームオーケストレーションに有用なコントロールペインは、次を表示する必要があります:

- アクティブな作業項目と、そのエージェントかんばんの状態。
- オーナー、ハーネス、ブランチ、worktree、および最後のハートビート。
- 引き継ぎ成果物、テスト、スクリーンショット、PR へのリンク。
- オーナーとブロック解除アクションごとにグループ化されたブロッカー。
- 感覚ではなく、ゲートごとのマージ準備状況。
- 共有スキルになるべき、再利用可能なワークフローの候補。

オペレーターが次の問いに答えられるようになるまでは、自動化を追加しないでください: 誰がこれを所有しているか、何が変わったか、どのゲートが失敗したか、何を安全にマージできるか。

## 動的ワークフローとの互換性

カードが動的ワークフローモードを必要とする場合:

- タスクローカルなハーネスはカードのオーナーの配下に置きます。
- 入力と出力はカードに保存します。
- Running から Review に移す前に評価を必須にします。
- 繰り返し使用された後にのみ、ハーネスを共有スキルに昇格させます。

## 注意すべき失敗モード

- **エージェントスープ**: 多数のエージェントが動いているが、オーナーもマージゲートもない。
- **見えない作業**: 有用な出力がチャットの記録の中にしか存在しない。
- **ボードの形骸化**: かんばんボードはあるが、カードに受け入れ基準がない。
- **書き込みの重複**: 並列エージェントが worktree なしで同じファイルを編集する。
- **プロダクト成果物なし**: プロセスがドキュメントは生むが、実行可能または公開可能なものを生まない。

## 出力基準

オーケストレーションの 1 サイクルごとに、次の内容で締めくくります:

- ボード/カードの変更。
- マージ済みまたは保留中のブランチ。
- テストと評価のエビデンス。
- オーナーと次のアクションを伴うブロッカー。
- 新しい共有スキルの候補。
