# recsys-pipeline-architect

組み合わせ可能なレコメンド、ランキング、フィードのパイプラインを構築するための、仕様とスキャフォールドのスキルです。xAI がオープンソース化した [For You アルゴリズム](https://github.com/xai-org/x-algorithm)（Apache 2.0）によって広まった **6 段階パターン**、すなわち Source → Hydrator → Filter → Scorer → Selector → SideEffect を組み込んでいます。このスキルはこのパターンの独立した再実装（MIT）であり、元のコードは一切コピーしていません。

アップストリーム: <https://github.com/mturac/recsys-pipeline-architect>

## 使用するタイミング

- ユーザーが「ユーザー/コンテキストに対する上位 K 件のアイテムを選ぶ」システムを構築したいとき
- ユーザーが「X をどうランク付けすべきか」と尋ねる、またはフィードやパーソナライゼーションの課題を説明したとき
- ユーザーがスコアリング関数を持っており、その周囲のパイプラインの配管を必要としているとき
- ユーザーが単一の関連度スコアから、調整可能な重み付きのマルチアクション予測へ移行したいとき
- ユーザーが LLM/ML スコアラーをラップしており、フィルタ、ハイドレータ、サイドエフェクト、そして自分のスタック（TypeScript / Go / Python）で動作するスキャフォールドを必要としているとき
- トリガー: "recommendation system"、"feed algorithm"、"ranking pipeline"、"for you feed"、"candidate pipeline"、"content recommender"、"pipeline architecture for recsys"、"RAG retrieval reranker"

## 使用しないタイミング

- モデルアーキテクチャの作業（Transformer の設計、two-tower リトリーバル、埋め込みの学習）— このスキルはモデルそのものではなく、モデルの*周囲*の配管を扱います
- 純粋な ML 学習パイプライン — スコアリング関数はユーザーの責任です
- デプロイ済みパイプラインの運用（監視、オートスケーリング）— 対象外です

## 6 段階フレームワーク

| # | ステージ | 役割 | 並列実行 |
|---|---|---|---|
| 1 | **Source** | 1 つ以上の取得元から候補を取得する | 可 — 複数のソースを並列に実行 |
| 2 | **Hydrator** | フィルタリングとスコアリングに必要なメタデータで各候補を補強する | 可 — 独立したハイドレータは並列に実行 |
| 3 | **Filter** | 表示すべきでない候補（ブロック済み、期限切れ、重複、対象外）を除外する | 逐次 — 各フィルタが見る件数は徐々に減る |
| 4 | **Scorer** | 残った各候補に 1 つ以上のスコアを割り当てる | 逐次 — 後段のスコアラーは前段のスコアを参照できる |
| 5 | **Selector** | 最終スコアで並べ替え、上位 K 件を返す | 単一の操作 |
| 6 | **SideEffect** | 配信済み ID のキャッシュ、インプレッションのログ記録、イベントの発行、カウンタの更新を行う | 非同期 — レスポンスを決してブロックしてはならない |

### なぜこの順序なのか

- ハイドレーションの前にソース: 補強にコストを払う前に、どんな候補が存在するかを把握する
- フィルタリングの前にハイドレーション: 多くのフィルタは、ソースが提供しなかったメタデータを必要とする
- スコアリングの前にフィルタリング: スコアリングは高コストなステージなので、対象外のものを先に除外する
- スコアラーはチェーン（単一のスコアラーではない）: 実際のシステムでは、ML スコアリング、多様性のリランキング、ビジネスルールを組み合わせる
- スコアリングの後に Selector: スコアリングを決定論的かつキャッシュ可能に保つ
- SideEffect は最後かつ非同期: サイドエフェクトがユーザーへのレスポンスをブロックしてはならない

## 呼び出し時のワークフロー

次の 8 つのステップに沿ってユーザーを案内します。

1. **ユースケースを明確にする**（1 ラウンド、3 つの質問）: ランク付けするアイテムは何か。入力コンテキストは何か。言語/ランタイムは何か。
2. **候補のソースを特定する**: 通常は、ネットワーク内（フォロー/所有/購読）と、ネットワーク外（ML 検索 / トレンド / 好きなものに似たもの）の組み合わせです
3. **必要なハイドレーションを列挙する**: 各フィルタとスコアラーについて、ソースが提供しなかったどのデータが必要かを確認します。
4. **フィルタを列挙する**: 重複、自己（ユーザー自身のアイテム）、古さ（経過時間）、ブロック/ミュート、配信済み、適格性。順序が重要です。低コストのものを高コストのものより先に置きます。
5. **スコアラーのチェーンを設計する**: プライマリ（ML）→ コンバイナ（重み付きのマルチアクション）→ 多様性 → ビジネスルール
6. **セレクタ**: 最終スコアの降順に並べ替えて上位 K 件を取る（ネットワーク内/ネットワーク外の層別ミックスでも可）
7. **SideEffects**: 配信済み ID のキャッシュ、インプレッションイベントの発行、カウンタの更新、分析ログの記録 — すべてファイア・アンド・フォーゲットで行う
8. **スキャフォールドを生成する**: ユーザーのスタックで生成する

## 明示すべき主要なトレードオフ（黙ってデフォルトにしない）

### 1. 単一スコア vs マルチアクション予測

- **単一スコア**: 関連度を予測するモデルを 1 つ学習する。挙動を変えるには再学習が必要。
- **マルチアクション**: 多数のアクション（閲覧、いいね、共有、スキップ、報告）について `P(action)` を予測し、サービング時に重みで組み合わせる。挙動を変えるには重みを変えるだけ。再学習は不要。

X の For You システムは、正の重みと負の重みの両方を持つマルチアクションを使用しています。ユーザーが頻繁に調整することを想定している場合は、マルチアクションを推奨してください。

### 2. スコアリングにおける候補の分離

- **分離（Isolated）**: 各候補を独立にスコアリングする。決定論的でキャッシュ可能。
- **結合（Joint）**: スコアリング中に候補同士が相互に注意を向ける（例: バッチに対する Transformer）。表現力は高いが、バッチ間で非決定論的になる。

デフォルトは分離にしてください。結合は、特定の理由（例: バッチを考慮した明示的な多様性）がある場合に限ります。

### 3. オンライン vs オフライン

- **リクエスト時（オンライン）**: リクエストごとにパイプラインを実行する。レイテンシ予算は 100〜300ms。デフォルト。
- **事前計算（オフラインバッチ）**: パイプラインを定期的に実行し、結果をキャッシュする。レイテンシは低いが、鮮度は下がる。
- **ハイブリッド**: 候補の検索はオフライン、ランキングはオンライン。

## 厳守ルール

1. **ベンチマークの数値を捏造しない。** 「どれくらい速くなるか」と聞かれたら →「ワークロードに依存します。ご自身で実行してください」と答える。
2. **帰属表示の徹底。** このパターンに言及するときは、「xAI がオープンソース化した For You アルゴリズムによって広まった」/ `github.com/xai-org/x-algorithm`（Apache 2.0）と明記する。
3. **商標を使用しない。** ユーザーの成果物に「X-like」という名前を付けたり、「For You」のブランドを使用したりしない。パターンは自由に使えるが、ブランドはそうではない。推奨する命名: "candidate pipeline"、"feed pipeline"、"ranking pipeline"、"recsys pipeline"。
4. **トレードオフを明示する。** マルチアクション vs 単一、分離 vs 結合、オンライン vs オフライン — 黙ってデフォルトにしない。
5. **生成するスキャフォールドは動作すること。** 擬似コードをコードとして出さない。
6. **フィルタの順序が重要。** 低コストのものを高コストのものより先に。汎用的なものをユーザー固有のものより先に。
7. **サイドエフェクトはブロックしない。** ファイア・アンド・フォーゲットのパターン（goroutine / await しない promise / asyncio タスク）でラップする。

## アンチパターン

- フィルタリングの前にスコアリングする（どうせ除外される候補に計算資源を浪費する）
- 同期的なサイドエフェクト（キャッシュ書き込みやインプレッション発行がレスポンスをブロックする）
- プロダクトが複数の目的（エンゲージメント、安全性、多様性、広告）に向けて調整する必要があるのに、単一の「関連度」スコアを使う
- 結合スコアリングをデフォルトにする（非決定論的でキャッシュしにくく、リランキングのステージと組み合わせにくい）
- 「説明のため」に擬似コードを生成する — スキャフォールドは実際に動作しなければならない
