# Itô Inference

`ito-inference` は、Itô コンピュート上の推論サービングに関する ECC 唯一の正規スキルです。`ito-serve` を指名するリクエストはここにルーティングされます。2 つ目の `ito-serve` スキルを作成またはインストールしてはいけません。ECC がノードへ SSH 接続すること、重みをダウンロードすること、エンジンを起動すること、エンドポイントを公開することは決してありません。また、予約、確保、支出も一切行いません。

## 現在の本番環境の境界

マネージドサービングは現時点では利用できません。ECC ブリッジが公開しているのは `login`、`auth`、`find`、`status`、および明示的にゲートされた `evals` のみです。`serve` サブコマンドは存在しません。正規ランタイムは `inference` をサポート対象外の互換性プローブとしてのみ文書化しており、ECC はこれを呼び出さず、依存もしません。MCP サーフェスが公開しているのは auth、find、status のみです。ローカルで強制できる保証は、ECC が認証情報を扱う正規クライアントを解決または起動する前に `serve` を拒否することです。

したがって、認証やコマンド呼び出しの前に停止してください。不足している機能を報告し、呼び出し元のエージェントに制御を戻します。ローカルランナー、SSH ヘルパー、ブラウザワークフロー、購入エンドポイント、追跡されていないローカルの `ito-serve` ドラフトで代替してはいけません。

## 必要なエンタイトルメント

サービングが実装された際、最初のゲートはサーバー側で検証済みの完了した予約です。ハーネスのメモリ、RFQ、見積もり、ノードの IP、SSH アクセスは、権限の証明にはなりません。バックエンドは、認証済みアカウント、予約、GPU トポロジー、リージョン、ファブリック、期間、モデルポリシーに紐づいた最新のサービング適格性を返さなければなりません。期限切れ、失効済み、不一致、不完全、またはすでに解放された予約は、承認の確認の前にフェイルクローズします。

## 将来の CLI と API の契約

意図されているコマンド名は `serve` です。`inference` は、本番契約が確定した後に、明示的に非推奨とされた互換エイリアスとしてのみ残すことができます。将来の引き渡しは、次と同等でなければなりません。

```sh
ecc ito serve \
  --booking <server-verified-booking-id> \
  --manifest <absolute-reviewed-json-file> \
  --confirmation-ref <opaque-non-authorizing-reference> \
  --idempotency-key <stable-retry-key> \
  --json
```

レビュー済みマニフェストには、モデルのリビジョン、エンジンとそのバージョン、量子化、テンソル/パイプライントポロジー、エンドポイント公開ポリシー、アーティファクトのチェックサム、ストレージ上限、ランタイム制限、任意の TTFT/TPOT 目標、および追加コストの上限を明記しなければなりません。生の API キー、SSH キー、ノードのパスワード、ベアラートークンは、引数、マニフェスト、ログ、MCP の結果、チャットのいずれにも含めてはいけません。

クライアントは、マニフェストのパスを正規化し、シンボリックリンクを拒否し、リンクをたどらずに通常ファイルを開き、適切な所有者と制限的なパーミッションを要求し、サイズに上限を設け、開いたディスクリプタから読み取ったバイト列をハッシュ化しなければなりません。そのダイジェストは、ワークロードを変更する前に、確認に紐づけられたダイジェストと完全に一致していなければなりません。パスのすり替え、ダイジェストの不一致、サイズ超過、または変更可能で安全でないファイルは、フェイルクローズします。

ワークロードの作成は ECC ではなく正規 API が担い、`ok`、`live_api_contacted`、`notice`、および `data` または `error` のいずれかを含む構造化 JSON を返さなければなりません。サービングのデータには、安定した予約 ID、ワークロード ID、マニフェスト ID、冪等性キー、および状態の列挙値を含めなければなりません。ヘルスチェックとモデルチェックに合格するまで、エンドポイントが稼働していると主張してはいけません。エラーには、安定したコードと、秘密情報を含まない安全なメッセージを含めなければなりません。

## 確認と実行のゲート

ワークロードを作成する前に、次のすべてを要求します。

1. 正規バックエンドからの最新のエンタイトルメントとサービング適格性。
2. レビュー可能で不変なマニフェストと、決定的なダイジェスト。
3. アカウント、アクション、マニフェスト、コストに紐づく、単回使用の個別の確認(承認)。有効期限は短く、リプレイ防止が施されていること。CLI 引数が運ぶのは、不透明で権限を持たない確認参照のみです。サーバーが帯域外でベアラー権限を解決し、消費します。
4. ワークロードとともにアトミックに確保される、呼び出し元指定の冪等性キー。
5. サーバー側でのファブリック、キャパシティ、モデルポリシー、ストレージ、コストの検証。

認証は ID の確認であり、ワークロードに対する権限ではありません。ログイン、API キー、見積もり、完了した予約のいずれも、サービングの確認の代わりにはなりません。検査とプラン生成でワークロードを作成してはいけません。キャンセルとクリーンアップは別個の変更操作であり、それぞれ固有のスコープ付き確認と冪等性の境界を持ちます。

## ライフサイクルと復旧

同じ正規クライアントが、テナントスコープのステータス、ログ、メトリクス、キャンセル、クリーンアップの各操作を公開するまで、本番サーフェスは未完成です。すべての操作には、接続と全体に対する上限付きのタイムアウト、失効を考慮したエラー、構造化された出力が必要です。曖昧なトランスポート障害の後は、再試行する前に冪等性キーでステータスを照会します。最初のレスポンスが失われたというだけの理由で、2 つ目のワークロードを作成してはいけません。失効した認証情報はポーリングを停止し、ログインを自動的に開始せずに、呼び出し元のエージェントに制御を戻します。

`ready` と報告してよいのは、エンドポイントのヘルス、モデルの同一性、カナリア推論のすべてに合格した後のみです。中間状態と終端の失敗状態は、正直に報告します。クリーンアップは観測可能でなければならず、その別個の経済的アクションが明示的に許可されていない限り、基盤となる予約を解放または変更してはいけません。

## 想定されるバックエンドのステージ

これらのステージは将来のバックエンドを記述したものであり、ECC に存在するコードではありません。

1. エンタイトルメント、トポロジー、ファブリック、コストのゲートを検証する。
2. チェックサム固定の重みを、バックエンド管理のストレージに取得する。
3. レビュー可能なトポロジー/エンジンのプランを出力し、検証する。
4. プロバイダのコントロールプレーン経由で起動する。ECC からの直接の root SSH は決して使わない。
5. ウォームアップを行い、ヘルスとモデルの同一性をテストし、SLO カナリアを実行したうえで、エンドポイントと秘匿化済みの設定を登録する。

上記のすべてのゲートとライフサイクル操作が正規ランタイムに存在するようになるまで、このスキルはフェイルクローズの可用性チェックおよびドキュメント上の引き継ぎにとどまります。
