# Brand Discovery

このスキルは、構造化され適応的なブランドアイデンティティ・インタビューを実施するために使用します。
ゴールは、完成した `90_SYNTHESIS.md` です。これは、組織がデザイナー、ライター、外部の協力者へのブリーフィングに使えるマスターブランドブックです。

インタビューは複数のセッションにわたって行われます。会話が終わっても引き出した知識が失われないように、また後のセッションが前回の中断箇所から再開できるように、回答は進めながらディスクに保存します。

## When to Activate

- ブランドを新規に作成する、リポジショニングする、または協力者へのブリーフィング用にブランドアイデンティティを文書化した参照資料が必要な場合。
- 複数セッションが想定される場合（会話が数日から数週間にわたる）。
- 複数の創業者やステークホルダーに対して、すり合わせ（リコンシリエーション）を行う前に個別のインタビューが必要な場合。
- ユーザーが場当たり的なチャットではなく、構造化された再現可能な手法を求めている場合。
- 既存のブランド文書が散在している、暗黙的である、または創業者に依存しており、明文化する必要がある場合。

## Session start protocol

起動のたびに、インタビューの質問を行う**前**に次の手順を実行します。

1. **これまでの進捗を確認する。** プロジェクトのブランドアイデンティティ用ディレクトリに、既存のモジュールファイル一式と `state.json` チェックポイントがあるか確認します。
   存在しない場合は新規開始です。ブランド名、参加者、ブランドアイデンティティ用ファイルの保存先を確認してから、最初のモジュールを開始します。
2. 進行中のモジュールがある場合は、**現在のモジュールファイルを読み**、Raw セクションをスキャンして、以前に記録された回答を確認します。
3. **ユーザーに報告する。** 2〜3 文で、現在どのモジュールにいるか、そのステータス、残りの作業を伝えます。その後、「ここから続けますか、それともモジュールを切り替えますか？」と尋ねます。

## Interview discipline

すべてのモジュールを通じて、次のルールを適用します。

1. **一度に 1 つの質問。** 質問のリストを提示してはいけません。
2. **各回答の後:** 短い言い換え → 深掘りの質問を 1 つ、またはトピックが飽和していればそのスレッドを閉じる。黙って次へ進んではいけません。
3. **ラダリング:** すべての「何を」の回答に対して、中核となる価値が現れるまで（通常は 2〜4 回の反復）「それはあなたにとってなぜ重要ですか？」と続けます。
4. **5 Whys:** 信念やポジショニングの主張に対して、表面的な宣言ではなく根本的な理由が出てくるまで掘り下げます。
5. **薄い回答を見抜く:** 回答が一般的、専門用語だらけ、または曖昧な場合は、具体例、クライアントの話、または数字を 1 つ求めます。
6. **投影法**（行き詰まりを打破するため、モジュールごとに 1 回使用）:
   - 「もしブランドが人だったら、その人はどのように部屋に入ってきますか？」
   - ブランドの訃報（オビチュアリー）: 「もし組織が 5 年後に閉鎖したら、顧客は何を惜しむでしょうか？ 言えなかったことで後悔するのは何でしょうか？」
   - 競合との対比: 「尊敬しているが、決してそうなりたくない同業者を 1 つ挙げてください。その相手がお手本として不適切なのは、具体的にどこですか？」
7. **飽和のシグナル:** 2 回連続の深掘りで新しい情報が出なかった場合は、要約してモジュールを閉じます。
8. **モジュールの終了:** 2 つのセクションを持つ構造化されたモジュールファイルを書き出します。
   - `## Raw` — 逐語の引用と例。
   - `## Synthesis` — あなたの解釈、3 つの候補となる定式化、未解決の問い、参加者間の矛盾。
   その後、`state.json` チェックポイントを更新します（下記の State protocol を参照）。

## State write protocol

各モジュールが飽和状態または完了ステータスに達した後、2 つのファイルを書き出します。

**モジュールファイル** は `modules/{moduleFile}` に配置します。Raw と Synthesis の全内容を含めます。

**`state.json`** は、後のセッションが再開できるようにするための軽量なチェックポイントです。
`completedModules`、`inProgressModule`、`nextModule`、`lastUpdated` を更新します。
スキーマ:

```json
{
  "session": "{brand_name}-brand-{YYYY-MM}",
  "outputPath": "{path_to_brand_identity_directory}",
  "completedModules": [],
  "inProgressModule": "10_purpose-why.md",
  "nextModule": "20_positioning.md",
  "participants": ["founder-A"],
  "lastUpdated": "{ISO-8601}"
}
```

書き出し後、「モジュール X を保存しました。状態を更新しました。次: Y。」と確認します。

**最終モジュール（90_SYNTHESIS.md）:** 最終的な統合文書を書くときは、`state.json` の `inProgressModule` を `"90_SYNTHESIS.md"` に、`nextModule` を `null` に設定します。書き出し後、`completedModules` に `"90_SYNTHESIS.md"` を含め、その後 `inProgressModule` を `null` に設定します。値が残ったままだと、後の再開時に完成済みのブランドブックがまだ進行中として扱われてしまいます。「ブランドブックが完成しました。すべてのモジュールを保存しました。」と確認します。

## Multi-founder mode

複数の創業者が参加する場合は、各創業者の回答をメインのモジュールファイルではなく `founders/{participant}.md` に書き出します。書き込む前に `participant` 名を検証します。許可するのは英数字とハイフンのみです（例: `founder-a`、`anna`）。パス区切り文字（`/`、`\`、`..`）や特殊文字を含む名前は拒否します。`moduleFile` は列挙されたモジュールシーケンス（10 から 90 のみ）に対して検証します。`outputPath` は、プロジェクトディレクトリ内の絶対パスであることを検証します。相対パスや `..` セグメントで外へ抜けるパスは拒否します。すべての創業者がモジュールを完了した後、すり合わせを実施します。モジュールファイルで収束点と相違点を要約し、グループのアラインメント・ワークショップに向けて「生産的な緊張関係」にフラグを立てます。

## Anti-Patterns

- **状態を読まずに開始する。** すべてのセッションは、既存のモジュールファイルと `state.json` を確認することから始めなければなりません。これを省略すると、以前のセッションからの連続性がすべて失われます。
- **複数の質問を一度に行う。** 一度に 1 つの質問というのは任意ではありません。リストはチェックリスト的な回答を生み、本当の洞察を生みません。
- **飽和する前に Synthesis へ進む。** 直近 2 回の深掘りで新しい情報が出なかったなら、そのモジュールは完了です。出たなら、まだ完了ではありません。
- **複数創業者のすり合わせを省略する。** 複数のステークホルダーが関わる場合は、すり合わせの前に個別のインタビューを完了しなければなりません。先に全員でブランドを議論すると、アンカリングバイアスが生じます。
- **これを 1 回で終わるセッションとして扱う。** このスキルは複数セッションを前提に設計されています。1 回の会話で `90_SYNTHESIS.md` に急ぐと、浅い成果物になります。
