# 並列実行オプティマイザー

速度が独立した作業の同時実行から得られる場合にこのスキルを使用します。
対象は、リポジトリの調査、ファイルの読み取り、API チェック、ブラウザチェック、ビルド/テストのレーン、
デプロイの読み戻し、複数 worktree での実装パスなどです。また、同種の作業でレコード間に変更のない準備が
繰り返される場合は、レコード操作が逐次のままでなければならないときでも使用します。

## コアパターン

行動する前に、緊急性を依存グラフに変換します。

1. 目的と完了シグナルを定義する。
2. 作業をレーンに分割する。
3. 各レーンを並列、逐次、またはゲート付きとしてマークする。
4. 独立した読み取り/チェックをまとめて実行する。
5. 書き込みをファイル、worktree、ブランチ、サービス、またはデータセット単位で分離する。
6. レーン同士が互換であることを示す証拠が得られてからのみマージする。
7. 曖昧な速度の主張ではなく、検証表で締めくくる。

## レーンマトリクス

大規模な作業に入る前に、簡潔なマトリクスを書きます。

```text
Lane | Can run in parallel? | Write surface | Risk | Verification
Repo scan | yes | none | low | rg/git status outputs
Backend patch | maybe | src/api | medium | unit tests
Frontend patch | maybe | app/components | medium | browser screenshot
Deploy readback | after build | remote service | high | live URL + logs
```

書き込み面が衝突しない場合にのみ、レーンを並列で実行します。

## 実行ルール

- ファイルの読み取り、検索、ステータスチェック、メタデータクエリはまとめて実行する。
- 大規模で無関係な実装レーンには、分離した worktree を使用する。
- 長時間実行されるテスト、ビルド、バックフィル、デプロイは別セッションで開始し、
  その後意図的にポーリングする。
- あるレーンが計画を変えるブロッカーを発見した場合は、依存するレーンを一時停止し、
  マトリクスを更新する。
- ユーザーが継続的なサービスを明示的に求めていない限り、バックグラウンドプロセスを
  ターンを超えて残さない。
- 破壊的なコマンド、マイグレーション、同じテーブルへの書き込み、顧客に影響するライブデプロイは、
  明示的なゲートなしに並列化しない。

## 限定的な同種作業

有限のレコードのグループが、マッピングやツールコントラクトなど、承認済みの不変な入力を共有している場合は、
準備を再利用します。これにより、繰り返される探索とタスクのセットアップが減ります。
同時書き込みは必要ありません。

1. 限定されたレコードセット、オーナーが定義した完了単位、順序、除外対象、完了シグナル、
   承認済みのマッピング/コントラクトのバージョン、再計画の条件を定義する。選択のカバレッジを
   承認済みのソース基準に照らして確認する。選択されたレコードだけを検証しても、
   セットが完全であることの証明にはならない。
2. 共有ソースを探索し、不変な入力を一度だけ準備する。そのバージョンと有効条件を記録し、
   それらの条件が成立している間のみ再利用する。
3. 各レコードに対する効果を適用する前に、現在のバージョン、権限、前提条件、意図する正確な効果を確認する。
   共有された準備は、共有された認可ではない。確認したバージョンに対する条件付き書き込み、
   介在する変更を検出するトランザクション、または確認と書き込みの間保持されるロックを必須とする。
   競合が発生したら停止し、そのような保護が利用できない場合は書き込まない。
4. そのレコードの実際の結果を検証する。検証された成功ごとに、そのレコードの証拠と残りの作業セットを
   引き継ぐ。書き込みを試みたことは、検証された成功ではない。結果が不確かな場合は、再試行する前に整合させる。
5. 実際の受け入れコントラクトが許す場合は、グループを 1 つのエグゼキューターで扱う。受け入れに別々の
   書き込み種別やステージが必要な場合は、その境界を維持し、検証済みで返されたキーとバージョンから
   次の許可されたステージを準備する。速度のために割り当てを広げたり、承認を迂回したりしない。
6. コントラクトと前提条件が有効である限り、同じ限定されたタスク内で継続する。成功のたびではなく、
   実際の依存関係、変更されたコントラクト、またはリスクが必要とする場合に、別のタスクまたはレビューを作成する。

### プランナー/エグゼキューターの例

以下は合成されたウォークスルーであり、測定されたランタイムのベンチマークでも、実行されたコネクターテストでもありません。
レコード A、B、C は独立しており、同じ承認済みマッピング M1 とツールコントラクト T1 を使用します。
書き込みは逐次のままです。

```text
Planner:
  group = [A, B, C]
  shared = accepted mapping M1 + tool contract T1 + source references
  verified = {}
  remaining = [A, B, C]

Executor for A:
  confirm shared inputs are still valid
  read A's current version; check permission and prerequisites
  determine exact effect; apply with the same conflict protection; verify outcome
  carry forward verified = {A: outcome evidence}, remaining = [B, C]

Executor for B, then C:
  reuse shared preparation and carried state
  repeat each record's version, permission, prerequisite, effect, outcome checks
  remove a record from remaining only after verifying its success

Replan:
  if T1 changes to T2, pause dependent work and review the changed contract
  if B's prerequisite fails, leave B unresolved and review that dependency
  preserve A's verified evidence; refresh only inputs invalidated by the change
```

引き継ぐ状態には、グループ、共有入力のバージョンと有効条件、レコードごとの検証済みの結果、
未解決/不確かな効果、残りのレコード、完了済み作業の除外、次に必要なチェックを含めます。
再開時には、変更された可能性のある入力を再検証します。新しいエグゼキューターが引き継いだというだけで、
完了済みの効果を再実行しません。新しいユーザーリクエストや変更されたスコープは、新しいコントラクトとして扱います。

### コネクター変更後の再開

合成されたハンドオフとして、A は完了済みで以後の変更から除外されており、B は効果がないことが
確認された上で失敗し、C は一度も試行されておらず、D は結果が曖昧であると仮定します。
これらの操作ごとの状態と証拠を、新しいコネクターのルートに引き継ぎます。A は除外したままにします。
再試行を検討する前に D を整合させます。実行可能なセットは、まだ認可されている未解決の作業から再構築し、
B と C はチェックに合格した後にのみ含めます。新しいツールコントラクトを検証し、意図する正確な効果を維持します。
元のバッチを実行可能なものとして再構築したり、後の試行が成功したからといって以前の逸脱を消去したりしません。

### 評価基準

このウォークスルーを使って、通常の成功が、変更のないソース探索やタスク全体の準備を繰り返すことなく
A → B → C と進むことを確認します。変更されたコントラクトや失敗した前提条件が、依然として該当する
レビューを引き起こすこと、レコードごとのチェックが損なわれないこと、未検証の結果が未解決のまま残ることを確認します。
コネクターの変更時には、完了済みの除外が維持されること、失敗した作業や未試行の作業には現在の認可が必要であること、
曖昧な効果が最初に整合されることを確認します。実際に実行されたことは、この提案された評価とは別に報告します。
この例から、レイテンシの改善や ECC/コネクターの障害の帰属を推測しません。

すでに準備の整ったグループについては、既存のジャーナルに、準備完了、ハンドオフ、最初のアクションの時刻を保持します。
必須のチェックと承認待ちを、コーディネーターの待機から切り分けます。クライアント側の呼び出しの重なりは、
バックエンドの並行性やスループットの向上を証明しません。GROUP_A の依存ステップが拒否された場合は、
そのステップを保留し、認可された独立した GROUP_B は進めてかまいません。オーナーの完了単位内の時系列順序と、
すべての除外されたレコード/区間を維持します。選択の表記ゆれのバリエーションと除外されたレコードを、
承認済みの基準に照らしてテストします。準備されていない書き込みの前に、選択から外れた適格な作業とオーバーフロー分を保持します。
バージョン競合や競合保護の欠如が、書き込みを発生させないことを確認します。
これらは提案された合成チェックであり、実行されたライブシステムの結果ではありません。

## 出力の形式

報告する際は次の形式を使用します。

```text
Parallel execution result:
- Lanes run: 5
- Lanes completed: 4
- Blocked lane: deploy readback, waiting on DNS propagation
- Fast path found: batched repo scan + focused tests
- Verification: lint pass, unit pass, live smoke pass
```

## 失敗モード

- 並行性を高めた結果、編集が競合する。
- タスクではなくツールをベンチマークしてしまう。
- 正しさが証明される前に「速い」ことを完了とみなす。
- 実行中のセッションをポーリングし忘れる。
- スキップしたチェックを成功の要約の陰に隠す。
