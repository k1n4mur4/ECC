# オーケストレーターパイプライン（共有エンジン）

`orch-*` スキルは薄いラッパーです。作業そのものを再実装することはなく、リクエストを分類し、*この*パイプラインのどのフェーズを実行するかを選び、各フェーズを既存の ECC エージェントまたはコマンドへ委譲します。このファイルがそのパイプラインです。

> このエンジンを直接呼び出すのではなく、操作スキル（`orch-add-feature`、`orch-fix-defect` など）を呼び出してください。このファイルは、それらが参照するリファレンスです。

## 使用するタイミング

- `orch-*` 操作スキルが実行されるたびに、間接的にロードされます。
- ファミリーに新しい操作を追加するとき、または共有フェーズ、ゲート、エージェントマップを調整するときのみ直接参照してください。

## 操作ファミリー

| スキル | 操作 | トリガー | 最初の一手 |
|-------|-----------|---------|------------|
| `orch-add-feature` | feature | 機能がまだ存在しない | 新しいスライスを調査して計画する |
| `orch-change-feature` | tweak | 動作はしているが、望ましい挙動が異なる | 既存の挙動*とそのテスト*を修正する |
| `orch-fix-defect` | fix | 壊れている。挙動が誤っている | 失敗するテストとして再現してから修正する |
| `orch-refine-code` | refactor | 挙動はそのままで、構造を改善する | テストをグリーンに保ちながら再構成する |
| `orch-build-mvp` | mvp | 設計書／仕様書からブートストラップする | ドキュメントを取り込む → 垂直スライスにする |

> これらのラッパーは既存の ECC コマンドを置き換えるのではなく**組み合わせます**。対象は `/feature-dev`、`/plan`、`/code-review`、`/build-fix`、`/refactor-clean`、`/gan-build`、および `tdd-workflow` スキルです。orch-* ファミリーは、共有のサイズ分類器と 2 つのゲートをそれらの上に追加し、1 つの包括的な仕組みで 5 つの操作すべてを一貫してカバーします。

## ステップ 0 — サイズを分類する（適正サイズ化）

プロセスの重さは影響範囲に比例させます。リクエストを 3 つのシグナルでスコアリングし、いずれかのシグナルが到達した**最も高い**ティアを採用して、ユーザーが上書きできるようにその結果を 1 行で述べます。

| ティア | 変更するファイル | 新しい依存関係／契約 | 設計の曖昧さ | 実行するフェーズ |
|------|---------------|---------------------------|------------------|-----------------|
| trivial | 1 つ、数行 | なし | なし — 変更が自明 | 4 → 5 → 6 |
| small | 1 ファイル／1 関数 | なし | コードを読めば明確 | (1 を軽く) → 4 → 5 → 6 |
| standard | 2〜5 ファイル | 新しい内部モジュールの可能性あり | 選択すべき本質的な分岐が 1 つ | 1 → 2 → 4 → 5 → 6 |
| large | 多数／横断的 | 新しい外部依存関係、パブリック API、または仕様書 | 未解決の問いが複数 | 1 → 2 → (3) → 4 → 5 → 6 |

フェーズ 0（Intake）は常に実行されるため、上の表の実行フェーズ列では省略しています。判断が分かれる場合の基準として、セキュリティトリガー（後述）またはパブリック API／契約に触れるものは、ファイル数にかかわらず**少なくとも** standard とします。

## フェーズ

各フェーズは委譲を行い、作業をインラインで行うことはありません。

- **0. Intake** — リクエストを自分の言葉で整理して再確認します。`orch-build-mvp` の場合は、仕様書／設計書を読み、スコープ、確定済みの決定事項、機能リストを抽出します。
- **1. Research & Reuse** — `rules/common/development-workflow.md` に従い、`gh search repos` / `gh search code`、次に Context7 / ベンダードキュメント、次にパッケージレジストリ、最後に Exa の順で調べます。新規コードよりも実績のある実装の採用を優先します。
- **2. Plan** — `planner` エージェント（構造上の決定には `architect` / `code-architect`）へ委譲します。薄い垂直スライスの順に並べた `task_list` を出力します。→ **GATE 1。**
- **3. Scaffold** — `orch-build-mvp` のみ：最初のエンドツーエンドのスライスを立ち上げます。
- **4. Implement (TDD)** — 各タスクを `tdd-guide` エージェント（または `tdd-workflow` スキル）で進めます。レッド → グリーン → リファクタリングの順です。操作ごとの最初の一手のルールに従います。
- **5. Review** — `code-reviewer` エージェント／`/code-review`。diff がセキュリティトリガー（後述）に触れる場合は、必ず `security-reviewer` を追加します。
- **6. Commit** — Conventional Commits（`feat:` / `fix:` / `refactor:` / …）で、論理的なまとまりごとに 1 つずつコミットします。→ **GATE 2。**

## 2 つのゲート

このファミリーは**ゲート付きであり、自律型ではありません**。

1. **GATE 1 — Plan の後。** `task_list` を提示します。ユーザーが承認するまで実装コードを書いてはいけません。
2. **GATE 2 — Commit の前。** diff の要約と提案するコミットメッセージを提示します。ユーザーが確認するまでコミットしてはいけません。

2 つのゲートの間の作業は、停止することなく進みます。

## エージェント／コマンドマップ

| フェーズ | 主担当 | フォールバック／エスカレーション |
|-------|---------|----------------------|
| Intake / 理解 | `code-explorer` | tweak、fix、refactor の前に既存のパスをたどる |
| Plan | `planner` | 構造上の判断には `architect`、`code-architect` |
| Implement | `tdd-guide`（または `tdd-workflow` スキル） | ビルドが壊れたときは `build-error-resolver` / `/build-fix` |
| Review | `code-reviewer` / `/code-review` | 言語別レビュアー（`python-reviewer`、`typescript-reviewer` など） |
| Security | `security-reviewer` | — |
| MVP 内部ループ | `/gan-build "<brief>" --skip-planner` | `gan-generator` → `gan-evaluator` を駆動します。`--max-iterations` / `--pass-threshold` で調整 |

言語別レビュアーはリポジトリに合わせて選びます（リポジトリ自身の `CLAUDE.md` を参照）。

## セキュリティレビューのトリガー

diff が次のいずれかに触れる場合は、`security-reviewer` を呼び出します。認証または認可、ユーザー入力の処理、データベースクエリ、ファイルシステムのパス、外部 API 呼び出し、暗号化、シークレット／認証情報です（`rules/common/security.md` に基づく）。

## 引き継ぎ成果物

パイプラインは隠れた状態を持ちません。計画ドキュメントそのものが引き継ぎ成果物です。

- （Plan で作成された）`task_list` が Implement ループを駆動します。
- 大規模な作業では、`rules/common/development-workflow.md` に従い、リポジトリの `docs/` 配下に PRD／アーキテクチャ／system_design も出力することがあります。
- レビューでの指摘（CRITICAL / HIGH）は、Gate 2 の前に解決する必要があります。

## 検証

- サイズティアが明示され、作業内容と一致していた
- Gate 1（計画）と Gate 2（コミット）の両方が守られた
- `security-reviewer` は、セキュリティトリガーに触れた場合に限り（かつその場合は必ず）実行された
- コミットが Conventional Commits 形式で、1 つの論理的な変更に収まっている
- 新規／変更された挙動にテストがある。カバレッジは `rules/common/testing.md` に従い 80% 以上
