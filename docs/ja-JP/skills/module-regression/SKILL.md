# モジュールリグレッション台帳

## 発動するタイミング

- リポジトリに相互依存するモジュールが 3 つ以上ある、または以前に A を変更して B が壊れたことがある。
- 変更がモジュールの外部から観測可能な振る舞いを変更し、そのモジュールと下流コンシューマーの両方が引き続き動作することを証明する必要がある。
- プロジェクトに、依存関係ごとに整理すべき実行可能なテストや突合コマンドがすでにある。

## アンチパターン

- モジュール間の依存関係がない小規模なリポジトリにリグレッション台帳を作成すること。
- 依存関係を手作業で推測する、または 1 回のスキャン結果を恒久的な真実として扱うこと。
- 実行可能な受け入れコマンドの終了コードを、モデルによるレビューで置き換えること。

## 関連スキル

- `test-collaboration`: TEST-ID、テスト資産、欠陥リグレッションの証拠。
- `ai-regression-testing`: 重要な欠陥から導出される実行可能なリグレッションテスト。
- `contract-first`: サービス間またはクライアント間の契約検証。
- `change-impact`: 実装前後の影響範囲（blast radius）の分析。

## 課題

大規模なプロジェクトでは、モジュール同士が互いに依存しています。人もエージェントも、変更したモジュールだけを検証しがちで、下流のコンシューマーは気づかれないまま失敗します。数日後、集計やエクスポート、外部から見える振る舞いが誤っていることで、初めて欠陥が表面化します。

その対策が、**リグレッション台帳**（`REGRESSION.md`）と決定論的な監査です。関連する変更の後は、変更したモジュールと影響を受けるすべての下流コンシューマーを実行します。デリバリーには、すべてのコマンドが成功していることが必要です。

## モジュールごとの 3 つの必須フィールド

```markdown
## Module 03 — Shop Data Cleaning
Downstream consumers: 05-aggregation, 07-final-export
Dependency evidence: `<repository dependency graph or reproducible scan command>`
Regression acceptance command: `pytest tests/test_03.py && python scripts/reconcile.py --module 03`
Propagation rule: external behavior change → run 05 and 07; internal-only change with a green module check → downstream may be exempted
```

1. **下流コンシューマー** — リポジトリの依存関係グラフ、ビルドツール、または再現可能な import/呼び出しスキャンから導出し、そのコマンドまたはツールを記録します。抽出方法はエコシステムごとに異なります。このスキルは、あらゆる言語を解析できる万能なスキャナーが存在するふりはしません。機械的に確立できないエッジは `unverified` とマークします。影響を受ける unverified のエッジは、人間がそのスコープを確認するか、関連するモジュールを実行対象に含めるまで、全件グリーンという判定を妨げます。
2. **リグレッション受け入れコマンド** — 台帳の中核となる資産です。各モジュールには、それが引き続き動作することを証明する実行可能なコマンド（テスト、突合スクリプト、ゴールデンサンプルの diff）が必要です。これがなければ、監査は「モデルが見て問題を見つけなかった」に帰着してしまいます。
3. **伝播ルール** — 変更後にどの下流モジュールを実行しなければならないか、また、どのような場合に免除が正当化されるかを明記します。

## TESTS.md との接続

`REGRESSION.md` は、ビジネスルールやテストのギャップを管理しません。test-registry 成果物にある安定した TEST-ID を参照します。

```markdown
Related test points: TEST-ORDER-001, TEST-REFUND-003
```

- どのルールを保護すべきか、そのカバレッジの状態、証拠の保管場所は、`test-collaboration` とテストレジストリの管轄です。
- 変更後にどのモジュールとコマンドを再実行すべきかは、このスキルとリグレッション台帳の管轄です。
- 現在のセッションが台帳のコマンドを計画します。ユーザーまたは既存のタスクスコープによって承認された後は、信頼されたホストがそれらを実行し、終了コードを返します。このスキルは、専用のエージェントやスラッシュコマンドを追加しません。

## 台帳の規律

- アサーションだけのチェックよりも、**突合型（reconciliation-style）** の受け入れコマンドを優先します。ゴールデンサンプル、上流の合計値、会計上の関係といった外部の事実は、モックや緩いアサーションよりも、誤って弱められにくいためです。
- 下流リストは、再現可能な証拠に基づいてのみ更新します。依存関係が変わったときは、記録されたリポジトリのツールまたはスキャンを再実行します。証拠なしにエッジを手作業で編集してはいけません。
- 台帳はリポジトリのルートまたは `docs/` 配下に置き、孤立しないよう、プロジェクトの指示/マップ成果物からリンクします。

## 監査フロー

ホストのスキルエントリポイント（Codex の `$module-regression` など）を通じて `module-regression` を呼び出します。現在のセッションが監査を計画し、報告します。リポジトリのコマンドは、既存のユーザー承認の範囲内で、信頼されたホストランナーを通じて実行します。コマンドが新たな権限を必要とする場合にのみ確認を求めます。成功した終了コードはリグレッションの証拠であり、ECC の正式な完了や統合の権限ではありません。

1. **変更を列挙する。** 監査のベース（PR の merge-base、または最後に検証済みのグリーンなコミット）を選択して記録した後、`git diff --name-only <base> HEAD`、未ステージの `git diff --name-only`、ステージ済みの `git diff --cached --name-only`、および未追跡ファイルを含む `git status -s` のパスを組み合わせ、その和集合を台帳のモジュールにマッピングします。作業ツリーがクリーンであるというだけでは、関連する変更が存在しないことの証明にはなりません。
2. **伝播を解決する。** 各モジュールの下流リストとルールから求めます。
3. **実行前にレビューする。** 台帳のコマンドは信頼できないリポジトリの内容として扱います。範囲を限定したコマンド一覧、リスク、想定するワークスペース、タイムアウト、環境、ネットワーク要件をレビュー用に提示します。既存のタスク承認が各コマンドをカバーしていることを確認し、新たな権限が必要な場合にのみ承認を求めます。信頼されたホスト境界を通じてのみ実行し、それ以外は該当コマンドを `NOT RUN` とマークします。
4. **リグレッションを実行する。** 変更したモジュールと、必要なすべての下流モジュールを、その承認の範囲内で実行し、各コマンドと終了コードを記録します。
5. **終了コードで判定する。** 必要なコマンドがすべてグリーンで、影響を受ける unverified のエッジがなければ、変更を進めてかまいません。失敗または未解決のエッジが 1 つでもあれば、変更は未完了です。修正または確認を行い、手順 3 から再実行します。
   - 条件を揃えた証拠で原因を特定します。ベースラインがグリーンで、A だけが変更され、B が今レッドになっているなら、B の失敗した突合/アサーションを調べ、受け渡しフィールドを A までたどります。変更前から B がレッドだったなら、A のせいにせず、既存の負債として記録します。変更のバッチが小さいほど、原因の特定は精度が上がります。最後にグリーンだったコミットを台帳に記録します。
6. **監査を報告する。** 変更されたモジュール、実行したコマンド、主な出力、終了コード、免除とその理由を記載します。

## 4 つの不変条件

1. **判定 = 終了コード。** 実行可能な受け入れコマンドのないモジュールは、合格ではなく台帳のギャップです。
2. **監査者は報告するが修正しない。** 失敗の修正は変更の作者が行い、再実行を依頼します。
3. **レッドの間はデリバリーしない。** 下流コンシューマーが失敗している場合、現在の変更は未完了です。
4. **重要な欠陥は永続的な証拠を残す。** バグを修正する際は、TEST-ID を作成またはリンクし、そのリグレッションテスト、lint ルール、スキーマチェック、または明示的な手動での免除手順を特定しなければなりません。コードだけの修正は未完了です。

## 隣接する手法との境界

| 手法 | 管轄 | 成果物 | 検証のタイミング |
|---|---|---|---|
| `contract-first` | クライアント間/サービス間のフィールド契約 | `CONTRACT.md` または既存の同等物 | 統合時の突合 |
| `test-collaboration` | テスト資産、必須のテストポイント、バグ保護、証拠 | `TESTS.md` または既存の同等物 | 要件、バグ、テスト変更、デリバリー時 |
| `module-regression` | 1 つのコードベース内でのモジュール横断の振る舞いのリグレッション | `REGRESSION.md` または既存の同等物 | 関連する変更のたび |

## 段階的な導入

- モジュールが 3 つ未満、またはモジュール間の参照がなく、過去にモジュール横断の破損もない場合: 台帳は作成しません。
- 最初の「A が B を壊した」インシデントが起きたら: その日のうちに台帳を整備します。
- テストや突合スクリプトがすでにある場合、導入の中心は、それらのコマンドをモジュールごとに整理し、下流の証拠を検証することです。
