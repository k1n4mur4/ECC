# Config GC — Claude Code セットアップのガベージコレクション

ランタイムのガベージコレクションから着想を得ています。参照されなくなったもの、冗長なもの、期限切れのもの、価値の低いものを定期的にスキャンし、領域を回収します。決定的な違いは、**ここでは回収に人間の関与が必須であることです。自律的に削除してはいけません。**

## 有効化するタイミング

- ユーザーが Claude Code の設定のクリーンアップ、監査、スリム化を求めたとき
- ユーザーがスキルの多さ、うるさいフック、セッション起動の遅さについて不満を述べたとき
- 月次・定期の設定レビューの時期が来たとき
- 大規模なスキルパック（例: このリポジトリ）をインストールした後、既存のセットアップとの重複を整理するとき

次の場合は有効化しないでください: プロジェクトのソースコードの整理（それはリファクタリングです）、チャット履歴の消去、Claude Code 自体のアンインストール。

## 設計思想

1. **追記のみの設定は漏れ続ける。** スキル、メモリファイル、フック、パーミッションエントリは増える一方です。定期的に見直さなければ、気づかないうちに腐っていきます。
2. **一度きりの一掃より、定期的な監査。** 約 30 日ごとにスキャンし、そのたびに少数のバッチを候補として提案します。
3. **チャネルごとの戦略。** 蓄積の種類（スキル、フック、パーミッションなど）ごとに固有の陳腐化シグナルがあります。すべてに同じルールを適用しないでください。
4. **まずソフトデリート。** `.disabled` へのリネームを最優先とし、次に `~/.claude/_gc_trash/` への移動、最後に実際の削除とします。常に元に戻す手段を残します。
5. **人間の関与を強制。** すべての候補に対して個別に `[y/n/skip]` で確認します。「すべて yes」のショートカットはありません。
6. **ログを残す。** GC の実行ごとに `~/.claude/gc_log.md` へ追記します。何に触れたか、なぜか、どう元に戻すかを記録します。

## スキャンチャネル

| # | チャネル | パス | 陳腐化・冗長性のシグナル |
|---|---------|------|--------------------------------|
| 1 | スキル | `~/.claude/skills/*/` | 名前が大きく重複している。最近のトランスクリプトで一度もトリガーされていない。ユーザーの実際の業務とドメインが合わない。SKILL.md が壊れている、または空 |
| 2 | メモリ | `~/.claude/**/memory/*.md` とそのインデックス | 1 つのトピックに複数のインデックスエントリがある。内容が新しいエントリと矛盾している。期日が過ぎている。インデックスにない孤立ファイル。統合すべき 100 語未満の断片 |
| 3 | フック | `~/.claude/hooks/` と設定 | ディスク上にあるがどのフック設定からも参照されていないスクリプト。書き直しによって置き換えられた古いバージョン |
| 4 | パーミッション | `settings.json` / `settings.local.json` の `permissions.allow` | 重複エントリ。ワイルドカードで既にカバーされている個別エントリ（例: `Bash(*)` が許可されているのに `Bash(git push)` がある）。過去の実験で付与した一回限りの許可 |
| 5 | MCP サーバー | `~/.claude.json` またはプロジェクトの `.mcp.json` | 接続に失敗するサーバー。機能が重複しているもの。長期間使われていないもの |
| 6 | スケジュール済みリマインダー / ジョブ | ユーザーが管理している場所 | 実行済みで 30 日以上経過した単発ジョブ。対象スクリプトがもう存在しないジョブ |
| 7 | プロジェクト履歴 | `~/.claude/projects/*/` | 古くなった引き継ぎスナップショット。新しい状態に置き換えられたセッション記録 |
| 8 | ランタイムキャッシュ | `cache/`、`file-history/`、`logs/`、`shell-snapshots/` | サイズと更新時刻でソートし、30 日以上経過していて大きいものを提案する |

## ワークフロー

1. **スキャン**: すべてのチャネル（またはユーザーが指定したサブセット）をスキャンします。候補ごとに、パス、チャネル、フラグを立てたシグナル、サイズ、最終更新日時を収集します。
2. **ランク付け**: 確信度順に並べ（壊れている・孤立している = 高、単に古いだけ = 低）、番号付きの表として提示します。1 回の実行で候補は約 20 件までに制限します。GC は定期的に行うもので、網羅的に行うものではありません。
3. **1 件ずつ確認**: 各候補について根拠を示したうえで `[y/n/skip]` を尋ねます。ユーザーはいつでも中断できます。
4. **確認済みの項目をソフトデリート**: スキルやフックは `.disabled` へのリネームを、ファイルは `_gc_trash/<date>/` への移動を優先します。パーミッションエントリは JSON にあるため（コメントを書けません）、設定ファイルをバックアップし、削除する各エントリを `gc_log.md` にそのまま記録してから、`jq` で `allow` 配列から削除します。ハードデリートは、ユーザーが明示的に求めた場合のみ行います。
5. **ログ記録**: 実行内容を `~/.claude/gc_log.md` に記録します。タイムスタンプ、処理した項目、元に戻す手順を含めます。
6. **報告**: 回収したサイズ、健全なままのチャネル、次回レビューの推奨日を報告します。

## スキャンコマンドの例

孤立したフックスクリプト（チャネル 3）— ディスク上にあるがどのフック設定からも参照されていないスクリプト:

```bash
for f in ~/.claude/hooks/*; do
  name=$(basename "$f")
  grep -rq "$name" ~/.claude/settings.json ~/.claude/settings.local.json 2>/dev/null \
    || echo "ORPHAN: $f"
done
```

冗長なパーミッションエントリ（チャネル 4）— 重複、およびワイルドカードに隠れている個別の許可:

```bash
jq -r '.permissions.allow[]' ~/.claude/settings.local.json | sort | uniq -d
if jq -e '.permissions.allow | index("Bash(*)")' ~/.claude/settings.local.json >/dev/null; then
  jq -r '.permissions.allow[]' ~/.claude/settings.local.json \
    | grep '^Bash(' | grep -vF 'Bash(*)'
fi
```

最大の陳腐化キャッシュ（チャネル 8）— GNU 専用の `find -printf` ではなく `du -k` を使うので、macOS/BSD でも動作します:

```bash
find ~/.claude/file-history ~/.claude/shell-snapshots -type f -mtime +30 \
  -exec du -k {} + 2>/dev/null | sort -rn | head -20
```

元に戻す手段を残すソフトデリート（ログとディレクトリで日付が食い違わないよう、日付は一度だけ取得します）:

```bash
gc_date=$(date +%Y-%m-%d)
mkdir -p ~/.claude/_gc_trash/$gc_date
mv ~/.claude/skills/dead-skill ~/.claude/_gc_trash/$gc_date/
echo "$(date -Iseconds) moved skills/dead-skill -> _gc_trash/$gc_date/ (undo: mv back)" >> ~/.claude/gc_log.md
```

冗長と確認されたパーミッションエントリの削除（JSON にはコメントがないため、バックアップ、ログ記録、編集の順に行います）:

```bash
cp ~/.claude/settings.local.json ~/.claude/settings.local.json.bak
echo "$(date -Iseconds) removed permission entry: Bash(git push) (undo: restore from .bak or re-add)" >> ~/.claude/gc_log.md
jq '.permissions.allow -= ["Bash(git push)"]' ~/.claude/settings.local.json.bak \
  > ~/.claude/settings.local.json
```

## アンチパターン

- **一括承認。** 「15 件すべて削除しますか？ [y/n]」と尋ねるのは、この設計を台無しにします。1 項目につき 1 回の判断です。
- **初回でのハードデリート。** `_gc_trash/` のコピーも `.disabled` へのリネームもないなら、やり方が間違っています。
- **「古い」を「死んでいる」とみなすこと。** 60 日間触れていないスキルが季節性のもの（確定申告の時期、四半期レビューなど）である可能性があります。経過時間はシグナルであって判決ではありません。だからこそ人間が確認します。
- **切り詰めによるメモリの整理。** 矛盾する 2 つのメモリファイルを統合するには、両方を読んで新しい方の事実を残す必要があります。長い方を削除してはいけません。
- **`~/.claude`（またはプロジェクトの `.claude/`）の外に触れること。** Config GC はソースツリーに立ち入りません。

## ベストプラクティス

- カレンダー上の日程だけでなく、大きな追加の後にも実行します。50 個のスキルパックをインストールした直後こそ、既存スキルとの重複が現れるタイミングです。
- 2 つのスキルが重複している場合は、トリガーの説明が弱い方を無効化することを優先します。おそらく元々トリガーされていなかった方です。
- パーミッションの整理は、かけた時間あたりの価値が最も高いチャネルです。冗長な許可エントリはセキュリティレビューを難しくします。
- `gc_log.md` は永久に保管します。サイズはごく小さく、「あのフックをいつ、なぜ無効化したか」という疑問は思っている以上によく出てきます。

## 関連スキル

- `skill-stocktake` — スキルの*品質*を監査します。config-gc はスキルの*存在*を監査します。GC を生き残ったものに対して stocktake を実行してください。
- `workspace-surface-audit` — 加算側の対となるもので、何をインストールすべきかを推奨します。config-gc は同じライフサイクルの減算側です。
- `configure-ecc` — これでスキルをインストールした後に config-gc を実行し、既存のセットアップとの重複を整理します。
- `continuous-learning` — このスキルが後で監査するメモリファイルを生成します。
- `security-review` — パーミッションチャネルと相性が良いです。
