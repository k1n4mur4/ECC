# レイテンシクリティカルシステム

ユーザーがリアルタイムの挙動、ホットパス、ストリーミングのフレッシュネス、または実行速度を重視している場合に、このスキルを使用します。HFT のようなインフラも対象に含まれますが、このスキルはエンジニアリングに焦点を当てたものです。実際の取引や金融アドバイスを許可するものではありません。

## メトリクスを分けて捉える

すべてを「速い」とひとまとめにしてはいけません。次の項目を追跡します。

- p50、p95、p99 レイテンシ
- スループット
- フレッシュネス経過時間
- キュー深度
- キャッシュヒット率
- プロバイダー/API の応答時間
- ブラウザのレンダリング時間
- 負荷下での正確性
- 障害とリトライの挙動

## ホットパスをマッピングする

ユーザー/イベントから最終的に見える状態までのパスを書き出します。

```text
source event -> provider API -> ingest worker -> queue -> cache -> edge route
-> client stream -> browser render -> user-visible state
```

そのうえで、各区間を個別に計測します。

## 最適化の順序

1. 不要なラウンドトリップを削除する。
2. 安定した読み取りをフレッシュネスのメタデータ付きでキャッシュする。
3. 小さな呼び出しや書き込みをバッチ化する。
4. 計算処理をデータまたはユーザーの近くに移す。
5. ホットパスとコールドパスを分離する。
6. キューが無制限に膨らむ前にバックプレッシャーをかける。
7. ストリーミングは、フレッシュネスまたはユーザー体験が向上する場合にのみ使用する。
8. 古いデータ、劣化したプロバイダー、不正なキャッシュ状態に対するカナリアを追加する。

## 検証

デプロイ済みのサーフェスがある場合は、ライブリードバックを使用します。

- HTTP のタイミングとレスポンスヘッダー
- プロバイダーのフレッシュネスタイムスタンプ
- キューまたはジョブの状態
- エッジ/キャッシュの状態
- 実際の UI のフレッシュネスを確認するためのブラウザ検証
- リトライや劣化モード周辺のログ

マーケットデータや実行に隣接するパスでは、そのパスが準備完了であると判断する前に、オーダーブックの経過時間、VWAP の前提、プロバイダーのステータス、キルスイッチの挙動も検証します。

## ガードレール

- 必要な検証を省略してレイテンシを最適化しないこと。
- 高速なキャッシュヒットの裏に古いデータを隠さないこと。
- 計測なしに、クライアント側のラベルだけでミリ秒レベルの挙動を主張しないこと。
- 明示的な承認ゲートなしに、実際の注文、破壊的なマイグレーション、顧客に影響するデプロイを実行しないこと。
- シークレットや非公開のペイロードを、ログやベンチマーク成果物に残さないこと。
